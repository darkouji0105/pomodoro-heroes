## 1. いま何がどうなっているか（**実コードで確認済み・2026-08-18**）

⚠ **必要な部品は全部ある。本番コードに手を入れずに書ける。**

| 要るもの | 実在するもの |
|---|---|
| 編成を決める | `GameManager.set_party_member(index: int, character_id: String) -> bool`（`game_manager.gd:1898`） |
| スキル枠を決める | `GameManager.select_skill(...)`（`game_manager.gd:2151`） |
| ステージを指定して戦闘へ | `SceneManager.change_scene_with_data(scene_path, data)`（`scene_manager.gd:50`）＋ `TransferKeys.STAGE_ID` / `STAGE_TYPE` |
| スキルを撃つ | ⚠ **`battle_controller._fire_skill(user, skill_id, power_ratio) -> bool`**（`:879`。戻り値は「撃てたか」） |
| 戦闘の記録 | `BattleLog` → `user://logs/battle_last.jsonl`（戦闘のたびに上書き） |

### 1-1. ⚠ 編成はステージが決めない（**間違えやすい**）

`stages.json` の `party_id` は ⚠ **`BattleLog` の見出しにしか使わない。メンバーは決めない**（`battle_session.gd:19`）。
⚠ **`stage_dbg_area` の `party_id` も `party_default` のまま。** メンバーは**状態（`PARTY_MEMBERS`）が唯一の正**（`battle_controller.gd:176`）。
→ ⚠ **検証用3体にするには `set_party_member()` を呼ぶしかない。**

### 1-2. ⚠ シーンを直接起動するとセーブが読まれない（**実測**）

`res://scenes/adventure/battle.tscn` を直接起動した回のログは `gold=100`（＝`initial_state` で初期化）で、⚠ **`load_state` の行が出ていない。** タイトル画面を通らないため。
→ ⚠ **`debug_boot` は「セーブを読まない状態」から始まる前提で書く。** ⚠ **読ませたい場合は明示的に呼ぶこと**（シナリオごとに決める）。

### 1-3. ⚠ `tests/` にはすでにデバッグ用が9件ある

`my_test` ／ `modal_test` ／ `dummy_scene_a` ／ `dummy_scene_b` ／ `base_screen_debug` ／ `pomodoro_core_loop_debug` ／ `test_ui_common` ／ `test_common_infra` ／ `battle/test_status_registry`（ほかに `debug_overlay.gd`）。
⚠ **「1個にまとめる」は、これ以上増やさないための決定でもある。** ⚠ **既存9件はこの回では触らない**（§0-1 の7）。

## 2. ⚠ 事故りやすい箇所

### 2-1. ⚠ **セーブを書かない**（この回で一番あり得る事故）

⚠ **`set_party_member()` と `select_skill()` は本物の状態を書き換える。** ⚠ **保存すると人間の編成とスキル枠が黙って変わる。**
→ ⚠ **`debug_boot` から `SaveManager` を1回も呼ばない。** ⚠ **「ついでに保存しておく」を絶対にやらない。**

### 2-2. ⚠ 本番コードを1行も触らない

⚠ **`_fire_skill()` は `_` 始まりだが、呼べる。** ⚠ **「公開関数が無いから `battle_controller` に足す」へ進まないこと。** 足したくなったら**そこで止めて人間に報告する**（`CLAUDE.md`「止まる条件」）。

### 2-3. ⚠ 撃つ合図を時間で書かない

⚠ **段階4で1回ぶん溶かした形そのもの**（t=2.32 で撃って判定不能）。⚠ **`await get_tree().create_timer(6.3)` と書かない。**
→ **敵が1回でも `damage` を出したこと**を合図にする（§0-1 の5）。

### 2-4. ⚠ `battle_last.jsonl` は戦闘のたびに上書き

⚠ **読む前に次のシナリオを走らせない。** ⚠ **連続で複数シナリオを回す作りにしない**（1回の起動＝1シナリオ）。

### 2-5. ⚠ ヘッドレスで意味のあるシナリオと、無いシナリオを混ぜない

⚠ **画面系（`training_screen` を開く等）はヘッドレスでは何も分からない。** ⚠ **シナリオ表に「窓あり専用」と書く**。書かないと、ヘッドレスで回して「通った」と誤読する。

### 2-6. ⚠ `--quit-after` を判定に使わない

⚠ **切れてもエラーが1つも出ない**（`EXEC_VERIFY_TOOLING.md` §1-7）。⚠ **`result` の行が出ているかで判定する。**

### 7-11. ⚠ 実装中に自分の決めを1つ取り消した（**§0-1 の5**）

⚠ **初稿の合図は「味方が1回でも殴られたら」だった。実測で弱いと分かったので変えた。**

- ⚠ **最初に殴ってきたのは `enemy_1_0`（射程300の置物）で、狼はまだ歩いていた**（t=5.59）。⚠ **殴られたことは「配置が整った」ことを保証しない**

### 7-12. ⚠ 実装中に踏んだこと（次に同じ形を書くとき用）

⚠ **`_ready()` の中では root に `add_child()` できないし、画面遷移もできない。** どちらも
`Parent node is busy ...` で弾かれる（`scene_manager.gd:24-26` が同じ理由で `call_deferred` している）。
→ ⚠ **`add_child.call_deferred()` と `change_scene_with_data.call_deferred()` の両方が要る。**

⚠ **さらに、遷移の枝は2つある**（`battle` は `change_scene_with_data` ／ `screen` は `change_scene`）。
⚠ **戦闘の枝だけ直して画面の枝を忘れ、人間が窓ありで実行して赤を踏んだ**（2026-08-18）。

- ⚠ **原因は検証漏れ。`area` と「引数なし」は走らせたが、`training` を一度も走らせずに渡した**
