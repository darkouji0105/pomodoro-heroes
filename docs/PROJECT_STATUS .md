## このゲームは何か

ポモドーロ（作業時間管理）をこなすと報酬がもらえる、拠点育成×簡易戦闘のハイブリッドゲーム。詳細は`CONCEPT.md`。

**設計原則（迷ったときの判断基準）**
- 「ポモドーロをやったらご褒美」という約束を裏切らない
- プレイヤーに「やって後悔した」と思わせない
- 頑張る楽しさを、素直に嬉しい手応えとして返す

## 実装の体制

### 役割分担

| 誰 | 役割 |
|---|---|
| **あなた** | 判断・実機検証・`.tres`と定数ファイルの編集・コミット |
| **設計役**（Claude） | PLANとEXECを書く。**壊れやすいコードは自分で書いて渡す** |
| **レビュー役**（DeepSeek） | PRE_PLANとIMPL_LOGをレビューする |
| **実装役**（MiniMax / Ziva） | PRE_PLANを書き、実装する |

詳細な手順は`WORKFLOW.md`。実装役に渡すプロンプトの全文は`docs/PROMPT_IMPL.md`（**Zivaには読ませない。人間が使う運用メモ**）。

### 設計役が直接コードを書く範囲（実測で確定）

以下は実装役に投げず、設計役が全文を書いて人間が差し替える。

- **200行を超える既存ファイルの変更**（`battle_controller.gd`など）
- **小さくて境界条件が多いもの**（`game_date.gd`の4時基準の日付判定）
- **状態機械やタイマーの整理**（`pomodoro.gd`のタイマーが3箇所から書き換えられていた件）

実装役に任せてよいのは、**新規ファイルの作成・JSONの作成・既存ファイルの末尾への追記**まで。この範囲は実測で問題なく通っている。

### 使うモデル

| モデル | 特徴 | 判定 |
|---|---|---|
| **MiniMax** | 迷った点を隠さず書く。実機で検証し、できなかった部分は正直に申告する。自分が壊した箇所も報告する | **採用** |
| Gemini | 難しい問題は解けるが、実際には動かしていない項目に「検証済み」と書く。完了条件を勝手に作り直す | 不採用 |
| GPT Luna | 未検証を正直に空欄で返すのは良いが、実機検証を丸ごと省く | 保留 |

**採用理由はコストではなく正直さ。** ただし「何としても完成させようとして止まらない」弱点がある（後述の事故一覧）。

## 次に何をすべきか

### 最優先：冒険選択画面

**ここでスタミナに使い道ができ、コアループが初めて閉じる。**

現状、ポーションを飲んでスタミナが増えても消費する先が一つもない。報酬の手応えが半分しか出ていないのはこのため。ステージに挑めるようになって初めて「作業する → 遊べる時間が増える」が成立する。

第2層が存在しないのでPLANから書く。`DATA_SCHEMA.md` 3章が土台。体験版のスコープは1〜10面（`DEMO_CHECKLIST.md`）。

**この画面ができるまで、戦闘のバランス調整はしない。** スタミナを払って挑む形になると1戦の重さの意味が変わるため、いま敵HPを調整しても測り直しになる。

### そのあと：バランス調整と手触りの確認

- 1戦の長さ（目標90秒前後。味方3人になって短くなっている可能性）
- チャージのジャスト窓（±0.15秒）と倍率（1.3倍）が気持ちいいか
- スタミナ消費量とポーション獲得レートの釣り合い
- 45分のしきい値、宝箱の素材4〜30個

**これらは全部JSONか`.tres`の値なので、後から変えられる。**

### その先

パーティ選択画面 → ギルドの残り（ショップ・育成・研究・作業場。すべてPLANあり）。

育成画面ができると、戦闘の味方生成が`character_growth`を読む経路に自動的に切り替わる（`battle_controller.gd`が既にその優先順で書かれている）。

### 判断に迷ったら

`CONCEPT.md`の設計原則に戻る。特に「プレイヤーに『やって後悔した』と思わせない」は、報酬設計・ペナルティ設計の判断基準として何度も使われている（宝箱の受け取りタイミング、ポーションの上限超え、チャージ失敗時の下限威力50%、敗北時にスタミナを再消費しない、など）。
