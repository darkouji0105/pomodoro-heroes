## 実装の進め方（確立済みの運用）

`AGENTS.md`「二段構え」に定義済み。実際に4タスク回して機能している。

```
【A】計画を書かせる → PRE_PLAN_◯◯.md
【B】人間が確認・修正指示
【C】PRE_PLANの末尾に「人間による決定事項」章を追記してから実装させる
【D】検証 + IMPL_LOG_◯◯.md 生成
【E】人間がIMPL_LOGをレビューし、必要なら差し戻し
```

### モデルの使い分け（実測）

| 座席 | モデル | 理由 |
|---|---|---|
| 【A】計画 | MiniMax | 出力が短いので安い。迷った点を隠さず書く。ただしファイル書き出しで詰まりやすいため、対策プロンプトが必要 |
| 【C】実装 | Gemini | 出力が長い座席には、やり直しの少ないモデルを置く |

**入れ替えないこと**：MiniMaxの弱点は「書き出しで詰まって何度も試行する」ことなので、出力が長い実装側に置くと損が大きい。

### 実測コスト

| タスク | 計画 | 実装 | 備考 |
|---|---|---|---|
| 拠点画面 | $0.13 | $0.25 + $0.13 | 差し戻し1回（型キャスト・完了条件の作り直し） |

### レビューで実際に見つかった失敗（対策は`AGENTS.md`に反映済み）

- 型認識エラーを回避するため`@onready`を`Node`型に落として`call()`で逃げた → ルールを緩めて回避することを禁止
- 完了条件20項目を自分で15項目に作り直し、検証しにくい項目が落ちた → EXECから項目ごと転記させる
- ツール（`edit_file` / `create_file`）で詰まって補助スクリプトを作り始めた → ツールの制約を明文化

**IMPL_LOGの「5. 指示書からの逸脱・迷った判断」は必ず読むこと。** 上の2件はどちらもここに正直に書かれていたから捕まえられた。

### 第3層を書くたびに守るルール（実コードとの突き合わせ）

PLANドキュメント（第2層）はあくまで「意図」の記録であり、実際に実装されたコードとは細部でズレる。このズレに気づかないまま次のEXECをPLAN記述だけで書くと、存在しない関数を呼ぶ指示書を渡すことになる。

- 新しい`EXEC_◯◯.md`を書く前に、そのタスクが依存する既存Autoload／既存シーンの**実コード（.gd/.tscn/.tres）を見せてもらい**、PLANの記述と突き合わせる
- ズレがあれば、まずそのズレをPLAN側に反映してから、EXECの中身を実コードに合わせて書く
- **`.tres`の中身も必ず確認する。** 拠点画面のときは`initial_state_config.tres`に値が入っていたが、`pomodoro_config.tres`は完全に空だった。空のまま実装すると作業時間が0秒になる
