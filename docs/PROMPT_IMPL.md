## 【C】実装させる

```
以下の4ファイルを読んでください。

1. AGENTS.md（プロジェクトルート）
2. res://docs/02_exec/EXEC_◯◯.md
3. res://docs/03_log/PRE_PLAN_◯◯.md
   §N「人間による決定事項」が最優先です。
   §1〜§N-1 と矛盾する場合は §N に従ってください。
   ［計画からの変更点があれば、その項番をここで名指しする］
4. res://docs/02_exec/IMPL_LOG_TEMPLATE.md

計画は承認済みです。§N の内容を反映した上で実装してください。

【今回やること】
［作るファイルを列挙する］

【人間が対応済みなので触らないこと】
［.tres / ja.csv / 定数ファイル / 200行超の既存ファイル など］

【止まってよい・止まるべき条件】
1つのファイルへの書き込みが2回失敗したら、そのファイルは諦めて、
次のファイルに進むか、そこで報告を返してください。

方法を変えても回数は増えます。cat で失敗して Python を試すのは2回目です。
キャッシュ削除・エディタ再起動・ファイルを消して作り直すのも1回に数えます。

「編集したのに反映されない」と感じたら、環境の問題だと判断する前に、
編集したファイルのパスが、実際に読み込まれているファイルと
同じかどうかを確認してください。

【未実装と書いてよい】
実装できなかったファイルは「未実装」と正直に書いてください。
埋めなくてよいです。できなかったと報告することは失敗ではありません。

無理に完成させようとして、指示書に無いファイルを作ったり、
別の手段を重ねたりしないでください。
中途半端に直った状態より、手を付けていない状態のほうが復旧が容易です。

【作業上の注意】
- edit_file は使わないでください
- create_file に長い本文を渡さないでください。
  150行を超えるファイルは bash の cat >> で分割してください
- 既存ファイルを cat > で上書きしないでください。追記は必ず cat >>
- 追記する前に、その内容が既に無いか確認してください
- 補助スクリプト（.py など）を作らないでください
- sed / awk を使わないでください
- 中間ファイルを経由した書き換え（/tmp に書いてから mv / cp）を
  しないでください
- 書き終わったあとに読み返して誤字を直す作業をしないでください。
  ただし既存ファイルに追記した直後だけは read で開き、
  編集前の内容が残っていることを確認してください（破壊チェック）
- .tres と autoload/ 配下は一切触らないでください
- project.godot は変更しないでください
- class_name が認識されないエラーが出たら Godot を再起動してください。
  型指定を Node に落として call() で回避しないでください

【検証について】
実装後、EXEC の「動作確認手順（完了条件）」N項目を
EXEC から項目番号ごと文言ごとそのまま転記し、
1項目ずつ実際に動かして確認してください。
項目を要約したり作り直したりしないでください。
完了条件のうち、確認するのは A章「実装役が確認する項目」だけです。
B章「人間が確認する項目」は、転記だけして検証しないでください。
検証しようとしないでください。原理的にできません。

書き方：
「[ ] 項目N：（EXECの文言をそのまま）」を先に書き、
改行してから検証結果を書いてください。
EXECの文言と検証結果を1つの文にまとめないでください。

「コードを確認した」「ロジック上正しい」は動作確認ではありません。
「何をしたら何と表示されたか」を書いてください。

［戦闘画面の場合］
検証には BattleDebugPanel を使ってください。
F3 でパネル表示、1〜4 で速度切替、K で敵1体撃破、
L でウェーブの敵を全滅、J で味方に10ダメージ、
V で強制勝利、B で強制敗北、S でクールダウンリセット。
速度を 4x や 8x にすると短時間で最終ウェーブまで到達できます。

実際に動かせなかった項目は [x] を付けず、
「実機未検証」と正直に書いてください。埋めなくてよいです。

【最後に必ず報告すること】
変更・作成したすべてのファイルについて、次の表を出してください。

| パス | 新規/変更/未実装 | 行数 |

行数は read で開いて数えた実際の値を書いてください。
EXEC の一覧に無いパスがこの表にあってはいけません。

そのうえで IMPL_LOG_TEMPLATE.md の型に沿って
res://docs/03_log/IMPL_LOG_◯◯.md を生成してください。
PRE_PLAN から変更した箇所があれば
「5. 指示書からの逸脱・迷った判断」に必ず書いてください。
```

## なぜこの形か（消さないこと）

過去に失敗して、その対策として入っている項目がある。理由を消すと、次の人が「冗長だ」と削る。

| 項目 | 入っている理由 |
|---|---|
| 「実機未検証と正直に書いてよい」 | 埋めさせようとすると嘘が混ざる。実際、動かしていない項目に「検証済み」と書かれた |
| 「未実装と書いてよい」 | これが無いと、完成させようとして指示書に無いファイルを作り、編集先を取り違えたまま「環境の不具合」と誤った原因分析を報告してくる |
| 「2回失敗したら止める」 | 旧「3回」は方法を変えると数え直されるため機能しなかった。6回試み続けた実例がある |
| 「変更ファイル一覧の表」 | 指示書に無いパスが増えていることを人間が一瞬で見つけられる。`git status` と同じ役割 |
| 「EXECの文言と検証結果を1文にまとめない」 | まとめられると元の条件が読めず、条件を満たしていない報告を見落とす |
| 「編集先のパスを確認」 | `battle_controller.gd` を直したつもりで別フォルダのファイルを編集していた |
| 「1回のツール呼び出しにつき見出し1つ」 | MiniMaxは同じ内容を2回書く癖がある。1回を短くすると起きにくい |
