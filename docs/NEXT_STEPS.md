# 次にやること：ギルドの作業場

**このファイルは「次の1タスク」だけを書く。** 終わったら次のタスクの内容に書き換える。全体の状況は`PROJECT_STATUS.md`、手順の型は`WORKFLOW.md`。

---

## なぜ作業場が次なのか

**素材とゴールドの出口はできた。残っているのは「時間を投資する」出口。**

```
戦闘で training_material / construction_material / gold を得る
  → 育成で training_material を使う      ✅ 済
  → 研究で construction_material を使う  ✅ 済
  → ショップで gold を使う               ✅ 済
  → 作業場で素材と「時間」を使う          ← ここ
```

ショップは即座に手に入る。作業場は**待つ**。この2つが並んで初めて「今すぐ欲しいか、安く手に入れたいか」の選択が生まれる。

---

## ショップと決定的に違うところ

**読み取り側が1つだけ本実装。**

| 関数 | 現在 |
|---|---|
| `get_crafting_queue()` | **本実装。** `_state`のキューを`duplicate(true)`して返す |
| `start_craft(recipe_id)` | `print`して`false`を返すだけ |
| `collect_craft(queue_id)` | `print`して`false`を返すだけ |

**ショップより難しい点が2つある。見積もりをショップと同じにしないこと。**

### 1. 完了判定がリアル時間になる

ショップのリフレッシュは「ゲーム内の日付が変わったか」で、`GameDate`の文字列比較1回で済んだ。

作業場は`started_at` + `duration_sec`と**現在時刻の比較**になる。**`GameDate`は1日の区切り専用で、経過時間の判定には使えない。** `Time.get_unix_time_from_system()`を直接使うことになる。

### 2. 画面が時間とともに変わる

育成・研究・ショップは**一度描いたら動かない画面**だった。作業場は残り時間を毎秒更新する必要がある。`_process`か`Timer`が要る。

**これまでのどの画面にも無かった要素。** 研究画面・ショップ画面の作りをそのまま流用できない部分がここ。

## このタスクでいま分かっていること

### 使えるもの

| もの | 状態 |
|---|---|
| 状態の構造 | `state_keys.gd`に一式ある（`RECIPES_UNLOCKED` / `CRAFTING_QUEUE` / `CRAFT_QUEUE_ID` / `CRAFT_RECIPE_ID` / `CRAFT_RECIPE_TYPE` / `CRAFT_STARTED_AT` / `CRAFT_DURATION_SEC` / `CRAFT_STATUS` / `CRAFT_OUTPUT_ITEM_ID` / `CRAFT_STATUS_IN_PROGRESS` / `CRAFT_STATUS_COMPLETED` / `CRAFT_STATUS_COLLECTED`）。**中身は空。編集は不要のはず** |
| `get_crafting_queue()` | **本実装済み** |
| `add_to_inventory()` / `add_material()` | **本実装済み。** 図鑑の`discovered`も自動で立つ |
| 素材の減算 | `add_material(id, -n)`。**残高を確認しないので、呼ぶ前に`get_material_count()`で確認する** |
| マスターと状態の同期の型 | **研究とショップで2回書いた`_sync_*_from_master()`。** レシピも同じ考え方で書ける |
| `MasterDataLoader` | `get_research_node()` / `get_shop_slots()` / `get_all_shop_types()`を末尾追記済み。**同じ形で`recipes.json`を足せる** |
| ショップ画面 | 1画面・スクロール・行をコードで生成。**作業場も同じ作りにできる**（ただし毎秒更新が加わる） |

### 決めることになるはず

- **何を作るのか。** ここが最大の未決定。下記「作るものの問題」
- **素材を消費するタイミング。** 開始時か、受け取り時か。**開始時が素直**（途中でキャンセルできない前提なら）
- **キューの本数。** 同時に何個まで走らせられるか。**第1弾は1本でいい**
- **`queue_id`をどう振るか。** `Time.get_unix_time_from_system()`ベースか連番か
- **オフラインで進むか。** `started_at`との比較なので**放っておいても進む。** これは決めるまでもなく、そうなる
- **キャンセルできるか。** 第1弾は**できなくていい**（素材が戻る処理が要らなくなる）
- **レシピの解放条件。** `recipes_unlocked`があるが、第1弾は**最初から全部解放でいい**

### スコープの目安

**第1弾は「レシピ3つ・キュー1本・キャンセルなし・開始時に素材消費」でいい。**

それだけで「素材と時間を入れる → 待つ → 何かが手に入る」が成立する。

**ポモドーロ連動（作業すると製作が進む）は第1弾に入れない。** `DATA_SCHEMA.md` 4-5に「詳細ロジックは未確定」と書かれたまま。リアル時間で進む形を先に作り、そのうえで「ポモドーロで短縮できる」を足すほうが分解しやすい。

### 作るものの問題

**装備アイテムが1つも存在しない。** ショップのときと同じ状況で、しかも作業場のほうが深刻。ショップは素材を売れば成立したが、**作業場が素材を消費して素材を作るのは意味が薄い。**

候補は3つ。**設計役と相談して決める。**

| 案 | 内容 | 評価 |
|---|---|---|
| **A. 素材の変換** | `construction_material` 20個 → `training_material` 30個（30分） | 実装は一番軽い。だが「取り合いを緩めるだけ」で新しい体験にならない |
| **B. スタミナポーションの製作** | 素材＋時間 → `stamina_potion` | 受け取り先が既にある（`ITEM_STAMINA_POTION`）。**遊べる量に直結するため、宝箱の中身の原則と衝突しないか要確認** |
| **C. 装備を先に作る** | 作業場より前に装備を1タスク入れる | 作業場の出力先が確定し、順番として自然。**ただし装備は`get_effective_stats()`への加算・スロット・戦闘反映がまとめて要る** |

**Cにするなら、このファイルは「次は装備」に書き換えることになる。** 判断は設計役に丸投げせず、実際にどれが遊んで面白いかで決めること。

### 見た目の注意

**ショップ画面と同じ作りにする。** 1画面・スクロール・行をコードで生成・詳細画面なし。

**戻るボタンは1つだけ。** 育成で2つ並んだ件を繰り返さない。

**残り時間の表示が要る。** ここだけは既存画面に前例が無い。

## 渡し方（ショップのときと同じ）

### 完了条件は「どこを見るか」で3つに分ける

**担当者（A章／B章）で分けない。** 実装役を使わないタスクが3回続いており、その分け方は機能しない。

| 種類 | 例 |
|---|---|
| **ログ** | 起動時の同期件数、`start_craft()` / `collect_craft()`の失敗理由 |
| **ファイル** | `save_slot_0.json`の`crafting_queue`（`started_at`が`float`で壊れていないか） |
| **画面** | レシピの表示・開始・残り時間の更新・受け取り・遷移 |

**同じことを2箇所に書かない。** 画面を操作すれば分かることは、画面の章にだけ書く。

**UIから到達できない項目（完了前の受け取り・存在しない`queue_id`）は人間の確認項目にしない。** 別枠にするか書かない。

### 待ち時間の検証をどうするか

**これはショップに無かった問題。** `duration_sec`が30分だと、完了の確認に30分待つことになる。

対策を先に決めておく：

- `recipes.json`に**10秒のテスト用レシピを1つ入れておく**（リリース前に消す）
- または`save_slot_0.json`の`started_at`を書き換えて過去にする（ショップの`refresh_at`と同じ手）

**EXECの完了条件に「30分待つ」と書かない。** 確実に飛ばされる。

### 誰が書くか

**育成・研究・ショップの3回とも、実装役に投げず設計役が`.gd`・`.tscn`・`.json`を全部書いた。事故ゼロ。**

作業場も同じ判断でよい。ただし`game_manager.gd`（**現在1323行**）に手を入れるので、**必ず設計役が全文を書く。** 原本をコピーして該当箇所だけ差し替える方式なら、既存関数が変質しない。

### 止まる条件（実装役を使う場合）

- 1つのファイルへの書き込みが2回失敗したら中止して報告
- 1つの症状に対して試す方法は2つまで
- 実装できなかったものは「未実装」と正直に書いてよい

## ショップで分かった罠（作業場でも踏む）

### `_copy_dict()`は浅いコピー

`_copy_dict(CRAFTING_QUEUE)`ではなく`_copy_array()`だが、**中の各エントリのDictionaryは`_state`と同じ実体を指す。** もう一段`duplicate(true)`してから書き換える。

### `MasterDataLoader`が返す数値は`float`

`duration_sec`・素材の個数は**必ず`int()`で包む。** 包み忘れるとセーブに`1800.0`と書かれる。

**`started_at`も同じ。** セーブから戻すと`float`になる。時刻の比較なので`float`のままでも動いてしまうが、**`load_state()`で`int()`に戻すこと**（`save_slot_0.json`に`1.7628e+09`と書かれると読めなくなる）。

### 状態を変える前に全部の判定を終える

ショップの`purchase_shop_item()`は「shop_type → slot存在 → 在庫 → 定義の妥当性 → 残高」を全部通してから状態を触る。作業場も「レシピ存在 → 解放済み → キューの空き → 素材」を先に全部確認する。

**定義の妥当性（出力アイテムIDが空でないか）を素材の判定より先に見る。** 素材だけ減って何も貰えない、が起きないようにするため。

### マスターの変更を既存セーブに反映する

研究・ショップと同じ形にすると、`duration_sec`やコストを変えたときに既存セーブへ反映される。

**進捗にあたるのは`recipes_unlocked`と`crafting_queue`。** ここだけ残す。

> **走っているキューの`duration_sec`をどう扱うかは要検討。** マスターで上書きすると、製作中にレシピを変えた場合に残り時間が飛ぶ。**キューには開始時点の値をコピーして持たせる**のが素直（`CRAFT_DURATION_SEC`がキュー側にあるのはそのため）。

### 1操作で複数のシグナルが飛ぶ画面は`await`を持たせない

受け取りは`inventory_changed`と（新設するなら）`crafting_queue_changed`を続けて発火する。**`queue_free()` + `await process_frame`で作り直すと行が二重に並ぶ。** `remove_child()`してから`queue_free()`する（`AGENTS.md`「再描画は await を持たせない」）。

### 検証手順は、その出力が実在することを確かめてから書く

育成で「ログで確認する」と書いたが、その`print`に該当項目が無かった。**書く前にコードを見る。**

## 作業場のあとの順番

1. **装備** — `get_effective_stats()`への加算まで含めて1タスク（**作業場より先に入れる可能性あり。上記「作るものの問題」C案**）
2. **パーティ選択** — 第2層から書く
3. **バランス調整** — ここで初めて実際に何日か使う

**装備が入るまで、本格的な試用はしない。** 数値の調整もそれまで待つ。全部JSONか`.tres`なので後から変えられる。

## 溜まっている宿題（気が向いたら）

`PROJECT_STATUS.md`の「溜まっている宿題」を参照。特に以下は小さいのに効く。

- **ショップの価格を実測して直す。** ステージ1周で何ゴールド入るかを測り、`shop.json`の`amount`を調整する。**再起動で既存セーブにも反映される**

- 受け取り報告で「宝箱を0個」と出るのを直す
- 拠点下部のレイアウト調整
- プロジェクト直下のゴミファイル（`bash`など）を削除
