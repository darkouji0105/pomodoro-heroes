## 1. 何が問題か

**`type` が2つの軸を1本に潰している。**

| 今の `type` | 対象の選び方 | 効果の種類 |
|---|---|---|
| `single` | 最も近い敵1体 | ダメージ |
| `aoe` | **敵全員固定** | ダメージ |
| `heal` | **味方全員固定** | 回復 |

このため、**組み合わせを変えたいだけの場合でも新しい `type` が要る。**

書けないもの：単体回復・前方2体・貫通・自分だけに効く効果・**多段・遅延・再発動・複数の効果を持つスキル**。

> **`aoe` は「範囲」ではなく「敵全員」。** 名前が実装より広く見えるのも、この潰れ方が原因。

## 2. 目標のスコープ（**先に決めた。ここが全部の前提**）

参考にするのは**トリッカル**。**演出主導の戦闘**であり、**攻撃判定はアニメーションが出す。**

**取りに行く表現力／取りに行かない表現力を、最初に線で分ける。**

| 取る | 取らない |
|---|---|
| **多段**（1つのスキルが複数回当たる） | プレイヤーが方向を狙う操作（スキルショット） |
| **遅延**（詠唱・着弾） | 壁・地形 |
| **再発動**（第2段・第3段） | 当たり判定の形 |
| **効果の組み合わせ**（ダメージ＋デバフ＋自分バフ） | |
| **持続**（buff / dot） | |
| **チャージ**（既にある） | |

> **座標は2次元にする予定**（横と高さ。ルーンのジャンプが関わる）。**ただし戦闘の2次元化はこの器より上流の基盤変更であり、このPLANの担当ではない。**
> **このPLANは「2次元になっても書き直さなくてよい形」でスキーマを書く**（10章）。

## 3. 決定：**3軸 ＋ パラメータ**（2026-08-15）

**`type` は廃止する。残さない。**

スキル1件を、**3つの軸**と、**軸にぶら下がるパラメータ**で表す。

| 軸 | 担当 | 値 |
|---|---|---|
| **`activation`** | **どう撃つか** | `instant` / `charge` / `recast` |
| **`target`** | **誰に当たるか** | 入れ子。4章 |
| **`effects[]`** | **何が起きるか** | 配列。5章 |

**この3つはすべて同じ構造を持つ**：**軸の値が決まると、読むパラメータが決まる。**

- `activation: charge` → `charge{}` を読む
- `target.mode: select` → `sort` / `count` を読む
- `effects[].type: damage` → `multiplier` / `attack_type` を読む

**軸に書くのは「分類」、パラメータに書くのは「数値」。** この区別を崩さない。

### 3-1. 全体の形

```json
"skill_x": {
  "name_key": "...", "user_character_id": "...",
  "unlock_level": 1, "cooldown_sec": 8.0,

  "activation": "charge",
  "charge": { "just_sec": 1.0, "just_window_sec": 0.15,
              "min_ratio": 0.5, "just_bonus": 1.3 },

  "phases": [
    {
      "target": { "team": "enemy", "mode": "select",
                  "sort": "nearest", "count": 1 },
      "effects": [
        { "type": "damage", "trigger": "event:hit1",
          "multiplier": 0.4, "attack_type": "physical" },
        { "type": "damage", "trigger": "event:hit2",
          "multiplier": 0.8, "attack_type": "physical" },
        { "type": "buff", "trigger": "cast",
          "stat": "atk", "value": 0.3, "duration_sec": 5.0,
          "target": { "team": "self" } }
      ]
    }
  ]
}
```

**ネストは3階層まで**（skill → phase → effect）。**`phases` は省略できる**（省略＝1段）。単発スキルは2階層で書ける。

### 3-2. 前の会話の決定を1つ覆した（**明記しておく**）

**「体数は `target` の名前に含める（`target_count` は作らない）」を撤回する。**

撤回の理由：**選び方が増えたため、名前で表すと爆発する。**

```
チーム 2 × 選び方 4（nearest / farthest / lowest_hp / highest_hp）× 体数 5 = 40通り
```

体数を名前に含める方針は、**選び方が2〜3種のうちだけ成立していた。** 「HP条件を敵にも味方にも」が要ると決まった時点で、直積がまるごと必要になり、合成名は冗長になる。

**代わりに `target.count` を欄として持つ**（4章）。**「書けるが意味の無い組み合わせ」が生まれる代償は受け入れ、resolver の検証で `push_error` する**（5-4）。

## 4. `target`（誰に当たるか）

**「場所」と「対象」は対等ではない。** 対象の選び方には、**入力と出力が逆な2つのモード**がある。

| モード | 入力 | 出力 |
|---|---|---|
| **選抜型** `select` | **体数** | 場所は結果。指定できない |
| **範囲型** `area` | **場所と広さ** | 体数は結果。指定できない |

**「HPが一番低い味方」に場所という入力は無い。** 逆に「ステージ中央」に体数という入力は無い。
**よって「場所」は `mode: area` のときだけ存在する欄。** 一方 **「対象（誰に効くか）」は両方のモードで必ず要る**（範囲型でも「当たるのは敵だけ」と書きたい）。

### 4-1. 欄の一覧

| 欄 | 値 | いつ読むか |
|---|---|---|
| `team` | `enemy` / `ally` / `self` | **常に** |
| `mode` | `select` / `area` | **常に** |
| `sort` | `nearest` / `farthest` / `lowest_hp` / `highest_hp` / `all` | `mode: select` |
| `count` | 整数 | `mode: select`（**`sort: all` では読まない**） |
| `origin` | `self` / `absolute` / `nearest_enemy` | `mode: area` |
| `offset` | `{ "x": 0.0, "y": 0.0 }` | `mode: area` |
| `radius` | 数値 | `mode: area` |

### 4-2. 決めておくこと（実装時に迷わないため）

- **敵味方は「使用者から見た相対」で定義する。** `enemy` = `user.team` の反対、`ally` = `user.team` と同じ。
  ⚠ **現在の resolver は `TEAM_ENEMY` / `TEAM_PARTY` を定数で直書きしている**（52行・72行・84行）。**`user.team` から導出する形に変える。** 現在の6件は全員が味方なので、**この変更で挙動は変わらない**
- **`team: ally` は使用者を含む**（現在の `_resolve_heal` と同じ）
- **`sort: lowest_hp` / `highest_hp` は「割合」で比べる**（`hp / max_hp`）。絶対値だと `max_hp` の大きい前衛が常に選ばれる
- **距離は現在 `abs(t.x - user.x)` の1次元。** 2次元化したら2次元距離になる。**JSONは変わらない**
- **同率のときは配列の先頭を採る。** 並び順は `parties.json`（現在は `[僧侶, 弓兵, 剣士]`）
- **生存者が `count` に満たなければ、いる分だけに当てる。** 空振りにしない
- **対象が0体なら何もせず空配列を返す**（今の `_resolve_single()` / `_resolve_aoe()` と同じ挙動を保つ）
- **対象は死者を含まない。** よって**蘇生はこの器では書けない**。要るまで足さない
- ⚠ **`BattleSession` には距離順・HP順の取得が無い。** `get_alive_units()` はチーム単位。**並べ替えは `SkillResolver` 側でやる**（`BattleSession` に寄せない。セッションは器のまま保つ）

### 4-3. 「全体」は `select` 側にだけ置く

`sort: all` と、`area` に半径∞を書くのは同じ結果になる。**同じことが2通りで書ける状態を作らない。**

- **`sort: all` が「全体」の唯一の書き方**
- **`area` は「全体ではない範囲」専用**

この決めのおかげで、**既存の `aoe` 3件は `area` の層を待たずに移行できる**（9章）。

## 5. `effects[]`（何が起きるか）

**配列。1つのスキルが複数の効果を持てる。**

### 5-1. なぜ配列にしたか

- **ダメージとデバフを兼ねるスキルが書ける**（吸血・反動・斬りながら自分を強化）
- **多段が書ける**（6章）。しかも**段ごとに倍率を変えられる**
- **`attack_type` の居場所が構造で決まる。** これまで `attack_type` は「`damage` のときだけ意味を持つ欄」がトップレベルに浮いており、**「`heal` には作らない」を文章で守る必要があった**。効果の中に入れれば、**heal 効果には最初から存在しない**

**後から配列化すると「全スキル＋resolver＋`DATA_SCHEMA.md`」の3箇所が同時に動く。** `skills.json` が6件で、セーブがスキルIDしか持たない**今が一番安い。**

### 5-2. 効果の欄

| 欄 | 内容 | 省略時 |
|---|---|---|
| `type` | `damage` / `heal` / `buff` / `dot` | 必須 |
| `trigger` | **いつ発火するか**（6章） | `"cast"` |
| `target` | **段の既定を上書きする**（吸血・自分バフ用） | 段の `target` |
| `charge_scales` | チャージ倍率が掛かるか | `true` |

**`type` ごとに読む欄**

| `type` | 読む欄 | 状態 |
|---|---|---|
| `damage` | `multiplier` / `attack_type`（`physical` / `magic`） | 実装済み |
| `heal` | `multiplier`。**常に `mag` 参照。`attack_type` の欄を作らない** | 実装済み |
| `buff` | `stat` / `value` / `duration_sec` | **段階3**（9章） |
| `dot` | `multiplier` / `attack_type` / `duration_sec` / `interval_sec` | **段階3**（9章） |

**`heal` に `attack_type` を作らない**のは既存の決定（`skill_resolver.gd` 88行のコメント）。回復が攻撃力依存だった事故を直したときのもの。**戻さないこと。**

**`buff` の効果値に `multiplier` を流用しない。** buff は最低でも「どのステータスを・どれだけ・何秒」の3つが要り、流用しても欄は減らない。`multiplier` は damage / heal が「ステータスに掛ける係数」として使っており、かつ**チャージが上書きする欄**でもあるため、意味を3つ持たせない。

### 5-3. チャージ倍率の掛かり方（**効果ごとに指定**）

**`charge_scales`（省略時 `true`）を効果ごとに持つ。**

一律に掛ける形も検討したが、**「ためてもデバフの秒数は伸びない」が書けない。** 自由度を採る。

**この決定があっても `SkillResolver` はチャージを知らないままでいられる**（7章）。

### 5-4. 壊れた組み合わせは resolver が `push_error` する

自由度を上げた代償として、**書けるが壊れている組み合わせが増える。**

例：`mode: area` なのに `radius` が無い／`type: buff` なのに `stat` が無い／`team: self` に `sort: lowest_hp`。

**resolver に検証を書き、`push_error` で見えるようにする。** 現在の `attack_type` の不正値処理（27〜30行。不正なら物理に落として `push_error`）と同じ形にする。**黙って既定値になるのが一番悪い。**

## 6. `trigger`（いつ発火するか）——**アニメーションと二重管理にしない**

### 6-1. なぜ「秒数」を書かないか

**攻撃判定が出る瞬間は、アニメーションが持っている。** JSONにも `interval_sec: 0.15` と書くと、**アニメを1コマ直すたびにJSONも直すことになり、必ずズレる。**

`CLAUDE.md` 4番「状態にマスターデータを複製しない」と同じ構造の事故になる。

**よって、効果には「いつ」ではなく「何をきっかけに」を書く。**

### 6-2. `trigger` の3つの形

| 書き方 | 意味 | いつ使う |
|---|---|---|
| `"cast"` | 発動と同時 | **既定。省略時これ** |
| `"event:hit1"` | **アニメーションが出すイベント** | 演出があるスキル（**本命**） |
| `"delay:0.3"` | 発動から0.3秒後 | **アニメがまだ無いときの仮置き** |

**多段は効果を並べて書く。** `repeat` のような欄は作らない。

```json
"effects": [
  { "type": "damage", "trigger": "event:hit1", "multiplier": 0.4, "attack_type": "physical" },
  { "type": "damage", "trigger": "event:hit2", "multiplier": 0.4, "attack_type": "physical" },
  { "type": "damage", "trigger": "event:hit3", "multiplier": 0.8, "attack_type": "physical" }
]
```

**`repeat` より表現力が高い**（段ごとに倍率を変えられる）。**発動ディレイも `trigger: "event:cast_end"` で書ける。**

### 6-3. イベント名は**連番**（決定）

- 攻撃判定 … **`hit1` から順番**
- 詠唱の終わり … **`cast_end`**

意味のある名前（`slash` / `impact`）にすると、**アニメを作る側と効果を書く側が別々に命名して食い違う。**

**これ以上増やさない。** 増やしたくなったら、そのとき合意する。

### 6-4. アニメーションは**先に決めなくてよい**（決定）

**危ないのは2つだけで、どちらも紙の上で決められる。**

| | 後から足しても安い | 後から足すと高い |
|---|---|---|
| アニメーション本体 | ✅ | |
| タイミングの値 | ✅ | |
| **イベント名の規約** | | ⚠ 6-3で決めた |
| **「効果は外部からの合図で発火する」という前提** | | ⚠ 6-5で決める |

### 6-5. 発火の経路は**1本にする**（決定・**ここが一番重要**）

```
                          ┌─ trigger: "cast"      → 発動した瞬間
実行中のスキル層が          ├─ trigger: "delay:0.3" → 新層のタイマー
効果を待ち行列に置く        └─ trigger: "event:hit1" → ビューからの合図
                                    ↓
                          全部おなじ「発火した」処理へ
                                    ↓
                              SkillResolver
```

**段階2では `cast` と `delay` だけ実装する。** アニメが入るとき足すのは**「ビューからの合図を待ち行列に流し込む分岐1本だけ」**で、新層の構造もJSONの形も `SkillResolver` も変わらない。

⚠ **段階2を「タイマー専用」で作ってはならない。** そうすると新層が「時間で進むもの」になり、アニメを繋ぐときに**新層の作り直し**になる。

### 6-6. 合図が来なかったとき・中断されたとき（決定）

**合図が来ないと、効果は永久に発火せず、静かに消える。** ダメージが出ないだけでエラーも出ない。**このプロジェクトが何度も踏んでいる形。**

- **待ち行列にタイムアウトを入れる。** 一定時間で合図が来なければ **`push_warning` を出す**。**発火させるか捨てるかは実装時に決めるが、警告は必ず出す**
- **中断されたら待ち行列の残りを捨てる**（使用者が死んだ・戦闘が終わった）。チャージの `_cancel_charge()` と同じ考え方に揃える

**この2つは新層の初回実装（段階2）に含める。** あとから入れる動機が湧かない。

## 7. 層の分け方と、`SkillResolver` の契約

### 7-1. 「実行中のスキル」層を新設する（決定）

**多段・遅延・再発動は、全部「時間」。** チャージが今うまくいっているのは、**時間が `power_ratio` という1つの数に潰れるから**であり、多段はそうならない。**発動後もどこかが時間を持ち続ける必要がある。**

`battle_controller.gd` は既に**912行**。ここに持たせると破綻する。

```
battle_controller   … 入力と表示だけ
       ↓ 発動を1個作る
実行中のスキル(新層) … タイムライン。多段・遅延・再発動・持続・待ち行列
       ↓ 「今この瞬間、この効果を、この対象に」
SkillResolver       … 1回ぶんの解決。時間を知らない ← 契約は変わらない
```

**この新層は、`buff` / `dot` が要求する層と、パッシブの条件発動が要求する層と、同一のもの**（`NEXT_STEPS.md` 3章が「無い」と言っている層）。**1つ作れば5つ片付く。**

⚠ **新層はビューを知る必要がある**（アニメーションの合図を受けるため）。**`SkillResolver` は今後もビューを知らない。**
**新層は「データとビューが出会う場所」になる。** ここの名前と責務をはっきり決めないと `battle_controller` に溶けて元に戻る。

### 7-2. `SkillResolver` の契約（**線引きの本体**）

**旧6章は「チャージという前例を守れ」と書いていた。それは根拠として弱い。** 前例は1件しかなく、たまたま効果が倍率そのものだったから畳み込めているだけに見える。**本当の線引きはこれ。**

> **`SkillResolver` は「1回ぶんの、確定したスキルデータ」を解く。**
> **時間を持たず、次のフレームを知らず、ノードを触らない。**
> **時間・入力・演出が絡むものは外側が解き、resolver には「実効スキルデータ」を渡す。**

`battle_controller.gd` 600〜601行の畳み込みは、`multiplier` 専用の仕掛けではない。**`skill_data` 全体の複製に対する上書き**なので、原理的にどの欄でも上書きできる。

**歯止めを1つ置く（決定）：**

> **実効スキルデータは、`skills.json` に書ける欄しか含んではならない。**
> **外側が resolver 専用の欄を足さないこと。**

これが無いと「外側だけが渡す隠し欄」が生まれ、resolver の契約がJSONと静かに分岐する。

**この歯止めの下では、`charge` の欄は resolver に見せなくてよい**（resolver は `charge` キーを読まない）。**現状がそのまま正しい形になる。**

## 8. `activation`（どう撃つか）

| 値 | 読むパラメータ | 状態 |
|---|---|---|
| `instant` | なし | 実装済み |
| `charge` | `charge: { just_sec, just_window_sec, min_ratio, just_bonus }` | **実装済み**（1件） |
| `recast` | `recast: { window_sec }` ＋ `phases[]` | **段階4**（9章） |

## 10. 2次元化との関係

**戦闘の2次元化はこの器より上流の基盤変更**であり、このPLANの担当ではない。**ただしスキーマ側を2次元の形で書いておけば、コストはほぼゼロ。**

| 1次元で書くと | 2次元対応の書き方 |
|---|---|
| `offset: 150.0` | **`offset: { "x": 150.0, "y": 0.0 }`** |
| `radius: 200.0` | `radius: 200.0`（円）。**変えなくてよい** |
| `sort: nearest` の距離 | `abs(t.x - u.x)` → 2次元距離。**JSONは変わらない** |

**今入れておくのは `offset` を `{x, y}` にする1点だけ。** 1次元のまま実装しても `y` を無視するだけで動き、2次元化のときにJSONを書き直さずに済む。

**高さに関する判定欄**（「空中の敵にだけ当たる」など）は**今決めない。** ルーンのジャンプの仕様が決まってから `target` に欄を足せば済み、**この構造は壊れない。**
