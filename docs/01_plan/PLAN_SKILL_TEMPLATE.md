## 1. 何が問題か

**`type` が2つの軸を1本に潰している。**

| 今の `type` | 対象の選び方 | 効果の種類 |
|---|---|---|
| `single` | 最も近い敵1体 | ダメージ |
| `aoe` | **敵全員固定** | ダメージ |
| `heal` | **味方全員固定** | 回復 |

このため、**組み合わせを変えたいだけの場合でも新しい `type` が要る。**

書けないもの：単体回復・前方2体・貫通・自分だけに効く効果・**多段・遅延・再発動・複数の効果を持つスキル**。

> **`aoe` は「範囲」ではなく「敵全員」。** 名前が実装より広く見えるのも、この潰れ方が原因。

⚠ **同じ病気を、この改訂で2件見つけた。** 欄が2つの意味を兼ねる形は、見つけ次第割る。

| 潰れている欄 | 割り方 |
|---|---|
| `user_character_id`（所有者 ＝ 発動者） | **12章で割る** |
| **`attack_type`**（攻撃側の参照元 ＝ 防御側の参照先） | ⚠ **3件目。割らずに治る。** `scale_from` を足すと攻撃側が抜け、**「どの防御で受けるか」だけに純化する**（5-2-1） |

⚠ **3件目は前2件と治し方が違う。** 欄を割るのではなく、**別の欄を足したら片方の意味が自然に抜けた。**
**同じ形は今後も出るので、「割る」だけを解法だと思わないこと。**

⚠ **初版は「取る／取らない」の2列だった。DLC前提では足りない。** **「器は持つが実装は後」を挟む。**

| 取る（今すぐ） | **器は持つ・実装は後** | 取らない |
|---|---|---|
| 多段・遅延・再発動 | 反射・シールド・吸収 | プレイヤーが方向を狙う操作 |
| 効果の組み合わせ | スタン・沈黙・束縛 | 壁・地形 |
| 持続（buff / dot） | 移動・ノックバック | 当たり判定の形 |
| チャージ | 召喚・設置・分裂 | **貫通・経路判定**（6-8） |
| **射程**（4-5） | 変身 | ステルス |
| | コンボ（15章） | |

> **座標は2次元にする予定**（横と高さ。ルーンのジャンプが関わる）。**戦闘の2次元化はこの器より上流の基盤変更であり、このPLANの担当ではない。**
> **このPLANは「2次元になっても書き直さなくてよい形」でスキーマを書く**（16章）。

### 2-1. 「拡張しやすく作る」の定義（**曖昧にしない**）

| | 拡張しやすい | 汎用的なだけ |
|---|---|---|
| 足すとき | **値を1個足す** | **層を1個足す** |
| 壊れる範囲 | その値だけ | 全部 |
| 例 | `sort` に `highest_atk` を足す | 「効果に任意のスクリプトを書ける」 |

⚠ **後者をやると、DLCキャラごとに例外コードが増える。** 器で書けないものを個別ハックで通すのが常に一番安く見えるため、20体目には誰も全体を把握できない。

**既に証明されている2例**：`trigger: "event:◯◯"` が任意文字列を取る（イベント名を増やしてもスキーマは変わらない）／7-2の歯止め（投射物の狙点を実行時に上書きする話が、器を変えずに通った）。

## 3. 決定：**4軸 ＋ 2層**

**`type` は廃止する。残さない。**

### 3-0. 軸と層を混ぜない（**訂正**）

⚠ **初稿は「6軸」と書いていたが、6つのうち4つしか軸ではない。**

**軸の定義は「JSONに欄があり、値が決まると読むパラメータが決まるもの」。** この定義に合うのは4つだけ。

| | 名前 | JSONの欄 | 値で読む欄が決まる | 章 |
|---|---|---|---|---|
| **軸1** | **`activation`** | ✅ スキル直下 | ✅ | 8 |
| **軸2** | **`target`** | ✅ 段の直下／効果ごとに上書き | ✅ | 4 |
| **軸3** | **`effects[]`** | ✅ 段の直下 | ✅ | 5 |
| **軸4** | **`host`** | ✅ **効果の欄**（5-2） | ✅ | 9 |
| **層1** | **発火源** | ❌ **欄が無い** | ❌ | 10 |
| **層2** | **介入点** | ❌ **欄が無い** | ❌ | 11 |

**発火源と介入点は「分類」ではなく「実装の置き場所」。** JSONに書くものではない。

> **これを「軸」と呼ぶと、この章が守ろうとしている「軸＝分類／パラメータ＝数値」の区別そのものが崩れる。**
> **内容は1つも変わらない。** 10-1 の `host` × 発火源の直積表も、20章の「後から変えられない7つ」もそのまま生きる。

### 3-1. 4つの軸

**すべて同じ構造を持つ**：**軸の値が決まると、読むパラメータが決まる。**

- `activation: charge` → `charge{}` を読む
- `target.mode: select` → `sort` / `count` を読む
- `effects[].type: damage` → `multiplier` / `attack_type` を読む
- `host: point` → 座標に紐づける

**軸に書くのは「分類」、パラメータに書くのは「数値」。** この区別を崩さない。

⚠ **キャラ案を十数件通しても、軸も層も1つも増えなかった**（26章）。増えたのは欄と値だけ。

### 3-2. 全体の形

```json
"skill_x": {
  "name_key": "...", "user_character_id": "...",
  "unlock_level": 1, "cooldown_sec": 8.0,

  "activation": "charge",
  "charge": { "just_sec": 1.0, "just_window_sec": 0.15,
              "min_ratio": 0.5, "just_bonus": 1.3 },

  "phases": [
    {
      "target": { "team": "enemy", "mode": "select",
                  "sort": "nearest", "count": 1, "range": 500.0 },
      "effects": [
        { "type": "damage", "trigger": "event:hit1",
          "multiplier": 0.4, "attack_type": "physical" },
        { "type": "damage", "trigger": "event:hit2",
          "multiplier": 0.8, "attack_type": "physical" },
        { "type": "buff", "trigger": "cast",
          "host": "unit", "stat": "atk", "value": 0.3,
          "duration_sec": 5.0, "target": { "team": "self" } }
      ]
    }
  ]
}
```

**ネストは3階層まで**（skill → phase → effect）。**`phases` は省略できる**（省略＝1段）。単発スキルは2階層で書ける。

### 3-3. 覆した決定（**明記しておく**）

| 決定 | 撤回した理由 |
|---|---|
| 「体数は `target` の名前に含める」 | 選び方が増えて直積が必要になった。→ `target.count` |
| 「`projectile` を `effect` の分岐に残す」 | **効果ではなく送り方**。未知の値として `push_error` に落ちるのが正しい |
| 「蘇生は書けない」（4-2） | ⚠ **自己復活のみ緩和**（14-4）。他人蘇生はまだ書けない |
| 「狙われない用の母集団除外欄は不要」 | ⚠ **2度覆した。** ホログラムは狙われるので不要 → **ゾンビが支援側から要求**（14-5） |
| 「壁・地形は取らない」 | **撤回不要。** 飛び道具無効化は壁ではなく**待ち行列の取り消し**（6-8） |

## 4. `target`（誰に当たるか）

**「場所」と「対象」は対等ではない。** 対象の選び方には、**入力と出力が逆な2つのモード**がある。

| モード | 入力 | 出力 |
|---|---|---|
| **選抜型** `select` | **体数** | 場所は結果。指定できない |
| **範囲型** `area` | **場所と広さ** | 体数は結果。指定できない |

**「HPが一番低い味方」に場所という入力は無い。** 逆に「ステージ中央」に体数という入力は無い。
**よって「場所」は `mode: area` のときだけ存在する欄。** 一方 **「対象（誰に効くか）」は両方のモードで必ず要る。**

### 4-1. 欄の一覧

| 欄 | 値 | いつ読むか |
|---|---|---|
| `team` | `enemy` / `ally` / `self` / **`source`** | **常に** |
| `mode` | `select` / `area` | **常に** |
| `sort` | `nearest` / `farthest` / `lowest_hp` / `highest_hp` / `all` | `mode: select` |
| `count` | 整数 | `mode: select`（**`sort: all` では読まない**） |
| **`range`** | 数値。**省略＝無制限** | **常に**（4-5） |
| `origin` | `self` / `absolute` / `nearest_enemy` | `mode: area` |
| `offset` | `{ "x": 0.0, "y": 0.0 }` | `mode: area` |
| `radius` | 数値 | `mode: area` |

⚠ **`team: source` は「きっかけになった相手」**（10-3）。購読で発火するとき、`sort` で選び直すと**別人に当たる。**

### 4-2. 決めておくこと（実装時に迷わないため）

- **敵味方は「使用者から見た相対」で定義する。** `enemy` = `user.team` の反対、`ally` = `user.team` と同じ。
  ⚠ **現在の resolver は `TEAM_ENEMY` / `TEAM_PARTY` を定数で直書きしている**（52行・72行・84行）。**`user.team` から導出する形に変える。** 現在の6件は全員が味方なので、**この変更で挙動は変わらない**
  ⚠ **これが「誰でも撃てる」の前提。** 敵・召喚獣・ホログラムが同じ口で通る（12-2）
- **`team: ally` は使用者を含む**（現在の `_resolve_heal` と同じ）
- **`sort: lowest_hp` / `highest_hp` は「割合」で比べる**（`hp / max_hp`）
- **距離は現在 `abs(t.x - user.x)` の1次元。** 2次元化したら2次元距離。**JSONは変わらない**
- **同率のときは配列の先頭を採る。** 並び順は `parties.json`
- **生存者が `count` に満たなければ、いる分だけに当てる。** 空振りにしない
- **対象が0体なら何もせず空配列を返す**
- **対象は死者を含まない。** ⚠ **他人蘇生はまだ書けない。自己復活は死亡の介入点で解く**（14-4）
- ⚠ **`BattleSession` には距離順・HP順の取得が無い。** **並べ替えは `SkillResolver` 側でやる**（セッションは器のまま保つ）

### 4-3. 「全体」は `select` 側にだけ置く

`sort: all` と、`area` に半径∞を書くのは同じ結果になる。**同じことが2通りで書ける状態を作らない。**

- **`sort: all` が「全体」の唯一の書き方**
- **`area` は「全体ではない範囲」専用**

この決めのおかげで、**既存の `aoe` 3件は `area` の層を待たずに移行できる**（17章）。

### 4-4. **対象はいつ確定するか**（決定）

> **cast 時に確定する。以降は選び直さない。保持するのは参照ではなく ID。**

**別々の理由から同じ結論が出た。**

| 要求元 | 理由 |
|---|---|
| 多段 | 途中で対象が死んだら**アニメは流れるが当たらない**（選び直すと生存者に吸われる） |
| 誘導する投射物 | **発射の瞬間にビューが対象を知る**必要がある。飛翔中に選び直せない |

- ⚠ **ID を持つ。参照だと解放された瞬間に壊れる**
- **空振りは正常系。** 4-2 の「0体なら空配列」がそのまま効く
- ⚠ **使用者の死と対象の死で挙動が違う**（前者は残りを破棄、後者は空振り）。非対称だが正しい

### 4-5. **射程 `range`**（決定）

⚠ **オート戦闘では射程が発動条件そのもの。** 無いと**剣士と弓兵が同じ挙動**になる。

> **射程は対象の母集団を絞るだけ。絞った結果が0体なら発動しない。**

**発動可否と絞り込みを別々に実装しない。** 二重管理になり必ずズレる。一本化すると、`sort: all` で遠い敵まで巻き込む事故も、**「撃ったのに何も起きずCDだけ消える」事故も同時に消える。**

⚠ **代償：発動前に対象選択を呼ぶ必要がある。** 4-4（投射物）と**同一の要求**。→ **段階1で対象選択を独立して呼べる形にする。**

- `mode: select` は**対象まで**、`mode: area` は**狙点まで**の距離
- **`stat` に `range` を持てる**（⚠ 変身で射程が変わるため必須・14-3）
- ⚠ **移動AIと噛み合う。スキル射程 < 攻撃射程 なら永久に撃てない**（足が止まるため）。**無音で死ぬ** → **ロード時に `push_error`。⚠ フォーム単位で検証する**
- ✅ **比較相手の「攻撃射程」は既にある**（`unit.attack_range`。0章）。⚠ **初稿は「ユニット側に攻撃射程が要る」と書いていたが誤り。** 足すのではなく**既存の値と突き合わせる**
  → **この検証は、スキル側に `range` を入れた時点で今日の数値で実行できる**（比較相手が実在するため）
- ⚠ **通常攻撃に射程があり、スキルに無いのが今の非対称。** 剣士と弓兵は**通常攻撃では既に区別されている**（`attack_range` がマスターに入っている）。**スキルだけが区別されていない**
- ⚠ **UI**：射程外のボタンは暗くする。毎フレームは軽い判定、発動時にフル判定。**ズレたら `push_warning`**
- ⚠ **数値は座標定数とセットで後決め**（味方200・敵900で**最短500**。遠隔ですら初期位置から届かない）

## 5. `effects[]`（何が起きるか）

**配列。1つのスキルが複数の効果を持てる。**

### 5-1. なぜ配列にしたか

- **ダメージとデバフを兼ねるスキルが書ける**（吸血・反動・斬りながら自分を強化）
- **多段が書ける**（6章）。しかも**段ごとに倍率を変えられる**
- **`attack_type` の居場所が構造で決まる**（heal 効果には最初から存在しない）

**後から配列化すると「全スキル＋resolver＋`DATA_SCHEMA.md`」が同時に動く。** `skills.json` が6件で、セーブがスキルIDしか持たない**今が一番安い。**

⚠ **DLCへの効き目が一番大きいのもこれ。** 「ダメージ＋自分バフ＋敵デバフ」が1スキルに書けるだけで、**組み合わせが掛け算で増える。** 判定の形を足すより安い。

### 5-2. 効果の欄

| 欄 | 内容 | 省略時 |
|---|---|---|
| `type` | 下表 | 必須 |
| `trigger` | **いつ発火するか**（6章） | `"cast"` |
| `host` | **どこに残るか**（9章） | `none` |
| `target` | **段の既定を上書きする**（吸血・自分バフ用） | 段の `target` |
| `charge_scales` | チャージ倍率が掛かるか | `true` |
| `chance` | 確率 | `1.0` |
| `scale_from` | **何でスケールするか**（5-5） | ⚠ **省略不可。`damage` / `heal` は必ず書く**（既定値を作らない） |

**`type` ごとに読む欄**

| `type` | 読む欄 | 段階 |
|---|---|---|
| `damage` | `multiplier` / `scale_from` / `attack_type`（`physical` / `magic` / **`true`**） | 1 |
| `heal` | `multiplier` / `scale_from`。**`attack_type` の欄を作らない** | 1 |
| `buff` | `stat` / `value` / `duration_sec`（または `until`） | 3 |
| `dot` | `multiplier` / `attack_type` / `duration_sec` / `interval_sec` | 3 |
| **`dispel`** | 消す対象の指定 | 3 |
| **`cancel`** | **待ち行列から取り消す**（6-8） | 3 |
| **`transform`** | 所持スキルIDを差し替える（14-3） | 後 |
| **`move`** | 位置を動かす（⚠ 2次元化待ち） | 後 |
| **`summon`** | `unit_id` / `duration_sec`（14-2） | 後 |

**`heal` に `attack_type` を作らない**のは既存の決定（`skill_resolver.gd` 88行）。回復が攻撃力依存だった事故を直したときのもの。**戻さないこと。**

> ⚠ **ただし `heal` に `scale_from` は書ける——というより必ず書く**（省略不可・段階1の実装で確定）。回復スキルには `"scale_from": "mag"` と明示する。**警告は出さない。**
> **過去の事故は「`heal` が黙って `atk` を見ていた」こと。** `scale_from` があれば `atk` を使うには**明示的に書かねばならず、「黙って」が構造上もう起きない。** 決定の趣旨は構造が守るので、禁止も警告も要らない。
>
> ⚠ **既定値そのものを作らなかった理由**（`EXEC_SKILL_TEMPLATE_PHASE1.md` 決定1-5）：既定を「常に `atk`」にすると `skill_holy_ray`（`magic`）が `mag` を見なくなって数字が変わる。既定を「`attack_type` が指す軸」にすると、**`attack_type` を「防御の参照先だけ」に純化したはずなのに攻撃側の意味がこっそり残る**（5-2-1 が治した病気の出戻り）。**書かせるのが一番安い。**

### 5-2-1. `attack_type` の意味を純化した（⚠ 1章の3件目・**足したら治ったタイプ**）

現在 `attack_type` は [skill_resolver.gd:101-107](scripts/systems/skill_resolver.gd#L101-L107) で**2つの仕事**をしている。

```
BattleFormula.damage(
    user.get_power(attack_type),      ← 攻撃側の参照元（atk か mag か）
    target.get_defense(attack_type),  ← 防御側の参照先（def か mdef か）
```

**`scale_from` が攻撃側を引き取ると、`attack_type` は「どの防御で受けるか」だけになる。**

| 値 | 参照する防御 |
|---|---|
| `physical` | `def` |
| `magic` | `mdef` |
| **`true`** | **無し（確定ダメージ）** |

⚠ **`true` は「2つ目の意味」ではなく、同じ意味の3つ目の値。** よって1章の病気には当たらない。**割って治すのではなく、`scale_from` を足したら自然に治ったタイプ。**

**これで `scale_from: "spd"` ＋ `attack_type: "physical"`（速さでスケールするが物理防御で軽減される）が書けるようになる。** 今は書けない。

⚠ **貫通%との棲み分けは 11-2。**

**`buff` の効果値に `multiplier` を流用しない。** buff は最低でも「どのステータスを・どれだけ・何秒」の3つが要る。`multiplier` は**チャージが上書きする欄**でもあり、意味を3つ持たせない。

⚠ **`dispel` と免疫を混ぜない。** 免疫・CC耐性は**状態付与の介入点**（11章）。

### 5-3. チャージ倍率の掛かり方（**効果ごとに指定**）

**`charge_scales`（省略時 `true`）を効果ごとに持つ。** 一律だと**「ためてもデバフの秒数は伸びない」が書けない。**

**この決定があっても `SkillResolver` はチャージを知らないままでいられる**（7章）。

### 5-4. 検証は**ロード時**にやる（改訂）

自由度を上げた代償として、**書けるが壊れている組み合わせが増える。**

例：`mode: area` なのに `radius` が無い／`type: buff` なのに `stat` が無い／`team: self` に `sort: lowest_hp`／`range` が負／`effects[].target` に `range`。

⚠ **旧版は「resolver が `push_error`」だったが、それだと実戦で使われるまで壊れていることが分からず、使うたびに出る。**

> **`MasterDataLoader` 側で起動時に全件検証する。** resolver 側の防御は残すが、主戦場はロード時。

**黙って既定値になるのが一番悪い。**

### 5-5. **スケール変数表**（⚠ **DLCで増える唯一の場所**）

**何でスケールするかを、名前 → 数値の対応表として1箇所に持つ。**

#### 5-5-1. 書き方

```
ダメージ ＝ multiplier × Σ( weight × 変数 )
```

```json
"scale_from": [
  { "source": "atk",           "of": "user",   "weight": 1.5 },
  { "source": "spd",           "of": "user",   "weight": 3.0 },
  { "source": "hp_lost_ratio", "of": "target", "weight": 400.0 }
]
```

| 欄 | 内容 |
|---|---|
| `source` | **変数表の名前**（5-5-2） |
| `of` | `user` / `target` / `source`（きっかけの相手・4-1） |
| `weight` | その変数の係数 |

- ⚠ **`multiplier` は1つのまま。** これでチャージの畳み込みも `charge_scales` も無傷（5-3・7-3）
- **`scale_from: "atk"` の文字列は省略形**（＝`[{source:"atk", of:"user", weight:1.0}]`）
- **今の6件は書かない**（既定：damage＝`atk` / heal＝`mag`）ので、**17章の移行表は1行も変わらない**

> ⚠ **DLCで増えるのは変数表の行だけ。** スキーマも resolver の構造も変わらない。**2-1「拡張しやすい＝値を1個足す」の実例。**

#### 5-5-2. 初期ラインナップと想定レンジ

⚠ **正規化しない。生値のまま、想定レンジを併記する。** 0〜1に揃えると実際の数値が式から消え、**バランス調整のとき何を触っているか分からなくなる。**

| 群 | 変数 | 想定レンジ | `weight` の桁 | 段階 |
|---|---|---|---|---|
| **10軸** | `hp` `atk` `mag` `def` `mdef` `atkspd` `haste` `crit_rate` `crit_dmg` **`spd`** | 50〜500 | 1.0前後 | **1** |
| **HP派生** | `hp_current` / `hp_lost` | 0〜max_hp | 1.0前後 | **1** |
| | `hp_ratio` / `hp_lost_ratio` | 0.0〜1.0 | **数百** | **1** |
| **位置** | `distance`（`user` と対象） | 0〜700 | 0.1前後 | **1** |
| | `height` / `height_ratio` | ⚠ **2次元化待ち** | — | 後 |
| **戦闘** | `elapsed_sec` / `alive_count_ally` / `alive_count_enemy` / `wave_index` | — | — | 3 |
| **状態** | `stack:<状態ID>` / `combo_count` | — | — | 3 |

✅ **段階1の分は実コードの受けが既にある。** [unit.gd:120](scripts/systems/unit.gd#L120) の `get_stat(stat_key: String)` が**文字列キーの汎用アクセサ**なので、10軸はそのまま引ける。`distance` は `abs(t.x - u.x)`（`battle_controller.gd` 378行に同じ計算が既にある）。

#### 5-5-3. ⚠ 評価タイミング（**混ぜない**）

| | いつ確定するか | 理由 |
|---|---|---|
| **`multiplier`** | **cast 時** | チャージが畳み込む（5-3） |
| **対象** | **cast 時** | 4-4で決定済み |
| **`scale_from` の変数** | ⚠ **発火時** | `height` は hit1 で空中・hit3 で着地している。**cast 時に読むと意味が消える** |

> **`multiplier` は「データ」、変数は「その瞬間の実測値」。**

✅ **発火時評価なので「途中でバフが乗ったら後の段が強くなる」が自然に書ける。** cast 時評価だと書けない。

#### 5-5-4. ⚠ 変数表に入れてよいもの・いけないもの（**唯一の制約**）

> **読んでも値が変わらないものだけを入れる。**

| | 可否 | 理由 |
|---|---|---|
| `spd` / `height_ratio` / `hp_lost_ratio` / `distance` | ✅ | 何度読んでも同じ |
| **乱数** | ✅ **入れてよい** | ⚠ 1発につき第1段で**1回しか評価されない**（11-0）。多段では段ごとに1回ずつ振られる（**望ましい挙動**） |
| ⚠ **「前回からの差分」「読むと消費されるもの」** | ❌ | **「前回」がどこを指すか決まらない**（前の段？前のスキル？前のフレーム？）。**これは変数ではなく状態のカウンター**（13-1） |

⚠ **変数表は実際に列挙できる形で持つ（自由文字列にしない）。** DLCで名前をtypoすると**黙って0になり「なぜか弱い」になる。** **ロード時に全件突き合わせて `push_error`**（5-4と同じ場所）。

## 6. `trigger` と待ち行列 ——**アニメーションと二重管理にしない**

### 6-1. なぜ「秒数」を書かないか

**攻撃判定が出る瞬間は、アニメーションが持っている。** JSONにも `interval_sec: 0.15` と書くと、**アニメを1コマ直すたびにJSONも直すことになり、必ずズレる。**

`CLAUDE.md` 4番「状態にマスターデータを複製しない」と同じ構造の事故になる。

**よって、効果には「いつ」ではなく「何をきっかけに」を書く。**

### 6-2. `trigger` の形

| 書き方 | 意味 | いつ使う |
|---|---|---|
| `"cast"` | 発動と同時 | **既定。省略時これ** |
| `"event:hit1"` | **アニメーションが出すイベント** | 演出があるスキル（**本命**） |
| `"delay:0.3"` | 発動から0.3秒後 | **アニメがまだ無いときの仮置き** |
| **`"charge_start"`** | **チャージ開始時** | ⚠ `cast` は**チャージ完了時**なので、開始時を指す値が別に要る（13-3） |

**多段は効果を並べて書く。** `repeat` のような欄は作らない（段ごとに倍率を変えられるため表現力が高い）。

### 6-3. イベント名は**連番**（決定）

- 攻撃判定 … **`hit1` から順番**
- 詠唱の終わり … **`cast_end`**

意味のある名前（`slash` / `impact`）にすると、**アニメを作る側と効果を書く側が別々に命名して食い違う。**

⚠ **合図を出すのは術者のアニメとは限らない**（弓は飛んでいった矢が出す）。**演出シーンが出す。**

### 6-4. アニメーションは**先に決めなくてよい**（決定）

| | 後から足しても安い | 後から足すと高い |
|---|---|---|
| アニメーション本体 | ✅ | |
| タイミングの値 | ✅ | |
| **イベント名の規約** | | ⚠ 6-3で決めた |
| **「効果は外部からの合図で発火する」という前提** | | ⚠ 6-5で決める |

### 6-5. 発火の経路は**1本にする**（決定・**ここが一番重要**）

```
                          ┌─ trigger: "cast"      → 発動した瞬間
実行中のスキル層が          ├─ trigger: "delay:0.3" → 新層のタイマー
効果を待ち行列に置く        └─ trigger: "event:hit1" → ビューからの合図
                                    ↓
                          全部おなじ「発火した」処理へ
                                    ↓
                              SkillResolver
```

**段階2では `cast` と `delay` だけ実装する。** アニメが入るとき足すのは**「ビューからの合図を待ち行列に流し込む分岐1本だけ」**で、新層の構造もJSONの形も `SkillResolver` も変わらない。

⚠ **段階2を「タイマー専用」で作ってはならない。** そうすると新層が「時間で進むもの」になり、アニメを繋ぐときに**新層の作り直し**になる。

### 6-6. 合図が来なかったとき・中断されたとき（決定）

**合図が来ないと、効果は永久に発火せず、静かに消える。** ダメージが出ないだけでエラーも出ない。**このプロジェクトが何度も踏んでいる形。**

- **待ち行列にタイムアウトを入れる。** 一定時間で合図が来なければ **`push_warning`**
- **中断されたら待ち行列の残りを捨てる**（使用者が死んだ・戦闘が終わった）
- ⚠ **中断時は状態も剥がす**（チャージをキャンセルしたのに軽減が残る、が起きる・13-3）

⚠ **3分類を混ぜない。**

| 状況 | 扱い |
|---|---|
| 合図が来た・対象0体 | **正常。** 静かに空振り |
| **狙点に着弾したが誰も居ない** | **正常。** 着弾は起きているので合図は来る |
| 合図そのものが来ない | **異常。** `push_warning` |

> **演出シーンの規約：外れても合図を出す。** これで異常系は「シーンが壊れている」だけに絞れる。

### 6-7. 投射物（決定）

**JSONに弾速も弧も書かない**（6-1と同じ理由。全部「いつ当たるか」の言い換え）。**スキルが持つのは演出シーンのIDだけ。**

| | `target` の書き方 |
|---|---|
| **誘導する** | `mode: select`。**cast 時にユニット確定**（4-4） |
| **誘導しない** | `mode: area`。**発射時に狙点を焼き付け、着弾時に解決** |

- ⚠ **新層の契約が1つ増える**：**新層は演出シーンに対象（ID）を渡し、演出シーンは合図を返す。** 7-1 の「データとビューが出会う場所」の中身がこれ
- **投射物は着弾点でのみ判定する**（⚠ 貫通は高度の欄が決まるまで作らない）
- **飛翔中に対象が消えたら、発射時の座標に飛び続けて空振り**
- ⚠ **誘導する投射物の寿命は演出側が持つ**（無限に追わせない）
- ⚠ **狙点の実行時上書きは、`offset` が `skills.json` に書ける欄なので7-2の歯止めを破らない**

### 6-8. **待ち行列は外から取り消せる**（決定・⚠ 後から変えられない）

⚠ **飛び道具の無効化は「壁」ではない。** 6-5 の形では、**飛んでいる矢の正体は「発火待ちの効果」**。

> **「消える」＝ 待ち行列から取り消す**（効果type `cancel`）。

**仕掛けは既にある**（6-6 の中断）。**新機構ではなく、既存の中断を外から・選択的にできるようにするだけ。**

| 要件 | 理由 |
|---|---|
| **待ち行列を外から参照・取り消しできる** | ⚠ **後から変えられない** |
| 要素に**種別タグ**（投射物／近接／魔法） | 条件のマッチングに要る |

⚠ **「スキルごとの private な待ち行列」として作ると外部から取り消せない。** 6-6 の中断は**自分で自分を捨てるだけ**なので、privateでも成立してしまう——**気づかずに閉じた作りにしやすい。**

**条件は既存部品で足りる**：種別（タグ）／回数（カウンター）／時間（`duration`）／範囲（`host`）。
⚠ **詠唱の中断が同時に開く**（相手の待ち行列を取り消す＝同じ操作）。

⚠ **介入点と混ぜない。**

| | タイミング | 見た目 |
|---|---|---|
| **待ち行列の取り消し** | **着弾前** | 矢が消える |
| ダメージの介入点 | 着弾後 | 矢は当たるが無傷 |

## 7. 層の分け方と、`SkillResolver` の契約

### 7-1. 「実行中のスキル」層を新設する（決定）

**多段・遅延・再発動は、全部「時間」。** チャージが今うまくいっているのは、**時間が `power_ratio` という1つの数に潰れるから**であり、多段はそうならない。

`battle_controller.gd` は既に**912行**。ここに持たせると破綻する。

```
battle_controller   … 入力と表示だけ
       ↓ 発動を1個作る
実行中のスキル(新層) … タイムライン。多段・遅延・再発動・待ち行列・演出シーンとの往復
       ↓ 「今この瞬間、この効果を、この対象に」
SkillResolver       … 1回ぶんの解決。時間を知らない ← 契約は変わらない
```

⚠ **新層はビューを知る必要がある。** `SkillResolver` は今後もビューを知らない。**新層は「データとビューが出会う場所」。**

### 7-2. ⚠ **「状態の器」は新層と別**（旧版の誤りを訂正）

**旧版は「1つ作れば5つ片付く」と書いていた。誤り。寿命の持ち主が違うものを1層に混ぜていた。**

| | 寿命 | 持つべき場所 |
|---|---|---|
| 多段・遅延・再発動 | **スキル発動1回ぶん** | 実行中のスキル層 |
| buff / dot / パッシブ / 罠 | **スキルより長い** | **状態の器（13章）** |

⚠ **混ぜると 6-6 の中断がそのまま適用され、術者が死んだ瞬間に敵のDoTが消える。**

**前者が後者に投げて終わる**形にする（`SkillResolver` が今そうであるように）。

### 7-3. `SkillResolver` の契約（**線引きの本体**）

> **`SkillResolver` は「1回ぶんの、確定したスキルデータ」を解く。**
> **時間を持たず、次のフレームを知らず、ノードを触らない。**
> **時間・入力・演出が絡むものは外側が解き、resolver には「実効スキルデータ」を渡す。**

**歯止め（決定）：**

> **実効スキルデータは、`skills.json` に書ける欄しか含んではならない。**

これが無いと「外側だけが渡す隠し欄」が生まれ、resolver の契約がJSONと静かに分岐する。

⚠ **入口は2つになる**（4-5・6-7の要求）。

| 入口 | 内容 |
|---|---|
| **対象を選ぶ** | 発動前・発射時に呼ぶ。射程で絞る |
| **効果を当てる** | 発火時に呼ぶ |

**どちらも時間を知らないので契約は保たれる。** ⚠ **段階1で分けておく。**

|---|---|---|
| `instant` | なし | 実装済み |
| `charge` | `charge: { just_sec, just_window_sec, min_ratio, just_bonus }` | **実装済み**（1件） |

| **`toggle`** | オン/オフ（14-3） | 後 |

  ⚠ **現在は `charge` 欄の有無で分岐している**（`battle_controller.gd` 493〜498行）。**軸を見る形に変える**

## 9. `host`（効果がどこに残るか）——**新設**

**「召喚」「罠」「バフ」「毒沼」「コンボ」は別々の機能に見えるが、違うのは宿り先だけ。**

| 値 | 意味 | 例 |
|---|---|---|
| `none` | 残らない | 通常のダメージ・回復 |
| `unit` | **ユニットに付く** | バフ・デバフ・DoT・**変身**・装備パッシブ |
| `point` | **座標に付く** | **罠・毒沼・設置地帯** |
| `battle` | **戦場全体に付く** | **コンボカウンター**・天候 |
| `spawn` | **新しいユニットが生える** | 召喚・分身・ホログラム |

> ⚠ **`unit` / `point` / `battle` は同じ器でよい。** 違うのは**何に紐づくか**だけで、寿命・発火・消滅は同じ。
> **状態の器は、紐づけ先を3種とも取れる形で作る**（13章）。**後から座標対応を足すと作り直しになる。**

**これだけで罠が基盤変更なしに通る。** ⚠ **罠・タレットは `point` なので、召喚の基盤を待たない。「その場に居て条件で発火するだけ」でAIも勝敗判定も要らない。召喚と同じ箱に入れないこと。**

## 10. 発火源（何をきっかけに動くか）——**新設**

| 値 | 意味 | 誰が出すか |
|---|---|---|
| **自分の実行** | `trigger`（6章） | 実行中のスキル層の待ち行列 |
| **購読** | 外の出来事に反応する | ダメージ処理・撃破・進入・攻撃など |
| **条件** | 毎フレーム評価する | 状態の器 |
| **周期** | 一定間隔 | ⚠ `dot` の `interval_sec` が既にこれ。分類されていないだけ |
| **`expire`** | **自分が消えるとき** | 状態の器 |

⚠ **`trigger` と購読を同じ欄にしてはならない**（6-5の一本道が壊れる）。**別の欄・別の名前。形は同じ**（きっかけ → `effects[]`）。

⚠ **`expire` は購読ではない**（購読は「外の出来事」、消滅は自分の出来事）。「時間切れで爆発する爆弾」「バフが剥がれたら回復」。

### 10-1. `host` × 発火源 —— **これで何が書けるか**

| 宿り先＼発火源 | 自分の実行 | **購読** | **条件** |
|---|---|---|---|
| `none` | ダメージ・回復・多段 | — | — |
| `unit` | バフ・DoT・変身 | **反射・カウンター・撃破強化・マーク** | HP依存強化・スタック閾値 |
| `point` | 毒沼・設置地帯 | **罠（踏まれたら）** | **オーラ（範囲内に居る間）** |
| `battle` | — | **コンボ** | 全体条件 |
| `spawn` | 召喚・分身 | 死亡時に生える | — |

⚠ **`none` × 購読が空なのは正しい。** 何も残らないものは、後の出来事に反応できない。

**機能を1個ずつ足すのではなく、2軸の直積で増える。**

### 10-2. **反応から生まれた行動は、さらなる反応を生まない**（決定・⚠ 横断ルール）

**印を1つ付けるだけで3つ同時に解ける。**

- 反射の無限ループ（反射持ち同士が殴り合う）
- **追撃の発散**（追撃も攻撃なら追撃に追撃が乗る）
- **コンボカウンターの水増し**

**軸5（購読）の初回実装に含める。** ⚠ 後から気づくと再現しづらい。

### 10-3. 購読は「誰が関わったか」を運ぶ

⚠ **きっかけになったユニットを指せないと、追撃も反射も書けない**（`sort` で選び直すと別人に当たる）。
→ **`target.team: source`**（4-1）。**軸5の設計時に決める。後付けが面倒。**

### 10-4. 通常攻撃は「攻撃した」合図を出す

⚠ **担当外に置いていたが、購読の対象として必須になった**（追撃・N回攻撃ごと・攻撃時発動）。
**器に乗せるかは別。合図だけは出す。**

## 11. 介入点（処理のどこに割り込むか）——**新設**

**カタログの「防御・生存」がほぼ全部これ1個で片付く。** 割り込む場所が無いものに、割り込みは足せない。

⚠ **`BattleFormula.damage()` は67行の static で、割り込む余地がゼロ。** **今なら数十行。後だと全呼び出し元が同時に動く。**

### 11-0. ⚠ **2段構え**（初稿の書き方を訂正）

初稿は「シールド → 軽減 → 反射」を1列に並べていたが、**この列には性質の違うものが2種類混ざっている。**

| 段 | 何をするか | まとめられるか |
|---|---|---|
| スケール変数 × `weight` | 数値を作る | ✅ |
| 軽減% ／ 貫通% | 数値を掛ける | ✅ |
| コンボ加算 | 数値を足す | ✅ |
| **シールドが吸収** | ⚠ **シールドの残量を減らす**（副作用） | ❌ |
| **反射** | ⚠ **別のユニットへの新しいダメージを生む**（出力が2つになる） | ❌ |
| HPが減る | 状態を変える | ❌ |

**上は「数値の加工」、下は「状態の書き換え」。** よって2段に分ける。

```
【第1段】数値を確定させる —— 1回だけ評価する
   Σ(weight × 変数) × multiplier × (1 - 軽減) × 貫通 × (1 + コンボ加算) …
        ↓ ここで数値が確定し、二度と再計算しない
【第2段】確定した数値を消費する
   シールドが吸う → 残りがHPを削る → 反射が「確定した数値」を読んで新しい1発を作る
```

> **これが守るべき不変条件：**
> **ダメージは1回だけ計算され、以降は「確定した数値」として持ち回される。式を2回評価しない。**

⚠ **これを守らないと、シールドと反射がそれぞれ式を読み直し、画面に出た数字と内部の数字が別々に育つ。** エラーは1つも出ない。

✅ **この不変条件のおかげで、変数表に乱数を入れてよくなる**（5-5-4）。第1段で1回しか評価されないため。

### 11-0-1. ⚠ ただし第1段を「1本の固定式」にしないこと

**中身を1回の流れにまとめるのはよいが、`BattleFormula` に固定の1行として書くと詰む。**

- **割り込む位置が増える**（「軽減の前に貫通」「シールドの後にコンボ」）。固定式だと**新しい介入を足すたびに式を書き換える**
- **途中の値が取り出せない**（「シールドが80吸収」を画面に出したい）

> **第1段は「順番に数値を加工していく1回の流れ」であって、「1本の数式」ではない。**
> **加工する側は後から足せる。ただし流れは1回しか通らない。**

### 11-1. 割り込む場所は**4つ**（同じ作り方・別々の場所）

| 対象 | 例 | 段階 |
|---|---|---|
| **ダメージ** | シールド・軽減・反射・**コンボ加算**・**貫通%**・**確定クリティカル** | **1** |
| 回復 | 被回復低下・回復量増加 | 3 |
| **状態の付与** | CC耐性・デバフ無効・免疫 | 3 |
| **死亡** | **HP1で耐える・復活・死亡時発動** | 3 |

⚠ **状態付与はダメージ処理を一切通らない。** 作らないとCC耐性キャラが**器の外の例外コード**になる。
⚠ **死亡も別。** 「HP1で耐える」はダメージの介入点ではなく**死亡の介入点**。

> ⚠ **全滅判定より、死亡の介入点が先。** これを明示しないと**戦闘が終わってから復活する**事故が起き、無音で壊れる。

**条件：段階1で「介入点という作り方」を確立する。** ブレると4箇所バラバラになる。

### 11-2. 決めておくこと

- ⚠ **反射で生んだダメージには印を付けて再反射させない**（10-2の印と同じもの）
- ⚠ **貫通% と 確定ダメージ（`attack_type: "true"`）は別物。両方ある**（初稿は「貫通%だけ作れば両方書ける」としていたが、**分ける**）

| | 何か | 貫通%が効くか | シールド・軽減が効くか |
|---|---|---|---|
| **`attack_type: "true"`** | ダメージの**種別**。最初から防御を参照しない（5-2-1） | ❌ **効かない（no-op）** | ✅ 効く |
| **貫通%**（介入点） | **物理/魔法ダメージへの修飾**。防御を何%無視するか | — | ✅ 効く |

  **貫通100%と確定ダメージは結果が同じでも成り立ちが違う。** 貫通は「防御を削る」、確定は「最初から防御の話をしていない」。
  ⚠ **装備やバフで貫通を積んでも、確定ダメージは1ミリも変わらないのが正しい挙動。**
  ⚠ **`true` に貫通%が乗ったら no-op にする**（エラーにはしない）。書いておかないと、**貫通を積んだのに確定ダメージが伸びない理由が分からなくなる**
- ✅ **確定クリティカルの上書き対象は既にある。** `BattleFormula.roll_crit()` の結果を介入点で `true` に固定するだけ（0章）。⚠ **初稿は「通常クリティカルが存在しない」と書いていたが誤り**
  → ⚠ **`is_crit` は `roll_crit()` の戻り値として `_apply_damage()` の中で作られる**（`skill_resolver.gd` 100行）。**介入点をどこに置くかで、上書きできるかが決まる。** 判定の後・ダメージ計算の前に割り込める形にすること
- ✅ **`SkillResolver` の契約は無傷。** resolver は「このダメージを作る」まで

|---|---|

## 16. 2次元化との関係

**戦闘の2次元化はこの器より上流の基盤変更**であり、このPLANの担当ではない。**ただしスキーマ側を2次元の形で書いておけば、コストはほぼゼロ。**

| 1次元で書くと | 2次元対応の書き方 |
|---|---|
| `offset: 150.0` | **`offset: { "x": 150.0, "y": 0.0 }`** |
| `radius: 200.0` | `radius: 200.0`（円）。**変えなくてよい** |
| `sort: nearest` の距離 | `abs(t.x - u.x)` → 2次元距離。**JSONは変わらない** |
| `range` の距離 | 同上。**JSONは変わらない** |

**今入れておくのは `offset` を `{x, y}` にする1点だけ。**

**高さに関する判定欄**（「空中の敵にだけ当たる」など）は**今決めない。** ルーンのジャンプの仕様が決まってから `target` に欄を足せば済み、**この構造は壊れない。**
⚠ **貫通・経路判定はここに紐づく**（6-7）。高度が決まるまで作らない。
