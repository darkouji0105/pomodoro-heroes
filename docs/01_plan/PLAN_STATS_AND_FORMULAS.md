## 1. 軸の持ち方（実装の型）

- [ ] **`_stat_keys()`の配列に足す。** `_recalc_stats()`も`get_effective_stats()`も`get_equipment_bonus()`も全部この配列をループしているので、**ここに足せば育成・研究・装備の合成が全部追従する**
- [ ] **％系は`int`で持つ**（`crit_rate: 25` ＝ 25%）。`float`だと`.0`が乗る
- [ ] **`spd`を`stats`から抜かない。** 抜くと既存セーブの`spd`が宙に浮く。`characters.json`の値が毎回使われる形にしておけば、後から動かしたくなったときに数字を入れるだけで済む
- [ ] **実数も％も同じ`stats`辞書に入れる**（別バケットにしない）

### 式は`.gd`に書く。`.tres`の文字列にしない

`character_config.gd`の`stat_growth_formula`は`Expression`を文字列で持っているが、**あれはレベルアップの瞬間にしか走らない。**

**攻撃間隔とクールダウンは毎フレーム参照される。** 文字列を毎フレーム`Expression`で評価する形にしてはいけない。

## 2. 上限の持ち方

- [ ] **`get_effective_stats()`は生の合計を返す。上限は使う瞬間に掛ける**

理由は2つ。

**上限値を変えたときに既存セーブが自動で追従する。**（研究・装備で3回使っている「状態にはIDと数字だけを持つ」と同じ考え方）

**育成画面で「上限に当たっている」ことが見える。** 丸めた値だけを持つと、プレイヤーは上限に当たっていることに気づけない。**気づかずに強化を続けるのが、いちばん後悔する形。**

- [ ] 上限値を置く`.tres`を作る（`StatConfig`など）。`min_attack_interval_sec` / `max_crit_rate` / `max_haste`

> **⚠ `.tres`は既定値を書き出さない。** 実際に効く数値は`.gd`の`@export`初期値にある。この罠で既に1件死んでいる（`PLAN_IMPLEMENTATION.md` 6章）。

## 3. 軸としては入れないもの

**議論して落とした。理由を残す。同じ提案が次の会話で出るため。**

**ただし護符が防御・生存系を担当することになったので、「軸に入れない」と「効果としては存在する」は両立する。**

| | 軸 | 護符 | 落とした理由（軸としての話） |
|---|---|---|---|
| **ライフスティール** | ✕ | パッシブ候補 | オートバトルでは攻撃時間が9割を超え、HP自動回復と片方が必ず死に軸になる。**剣士の生存が剣士で完結すると、僧侶の存在意義が薄くなる** |
| **HP自動回復** | ✕ | **○ 採用** | 上記の裏返し。戦闘中だけなら誤差、ウェーブ間に効くなら僧侶の代替。**→ ウェーブ間の回復として護符で採用された** |
| **回避** | ✕ | **○ 採用（上限20%程度）** | 分散の向きが「下振れ」。避けたことには気づかず、避けなかったときだけ運が悪いと感じる。`def`を除算にした以上、**軸にすると2本目の減算経路になる**。**→ 上限20%の護符効果なら「たまに得する」に収まる** |
| **属性防御** | ✕ | ✕ | 意味を持つのは「ステージごとに正解の装備が変わる」ときだけ。**「炎耐性の兜を3時間かけて作ったら次は氷だった」が起きる** |

### 属性防御を落とした理由は、`def`/`mdef`の2軸には当てはまらない

**プリセットが2階層になり、パーティ選択画面で切り替えられるようになったため。** 装備を組み替えずに別ビルドで対応できる（`GAME_DESIGN.md` 8-1）。

## 4. データに増えるもの

- [ ] `characters.json`に各キャラの基礎値（**軸の数は8-1を見る**）
- [ ] `characters.json`に`allocatable_stats`（振れる軸はキャラごとに違う。`GAME_DESIGN.md` 5-3）
- [ ] `skills.json`に「`atk`と`mag`のどちらを参照するか」の欄
  - **着手時に`skills.json`を見て、欄が無ければ追加する**

### `growth_per_level`に％系を入れない

レベルで`crit_rate`が伸びると、レベル100で勝手に100%に達する。**％系は装備と装飾だけで動かす。そうしないと紋章を刺す理由が消える。**

**同じ制約が割り振りポイントにも適用される**（`GAME_DESIGN.md` 5-3）。振れるのは実数軸のみ。

**なお、レベルでステータスが上がらないと決めたため（`stat_growth_formula = "base"`）、`growth_per_level`は当面読まれない。消さずに残す。**

### `mag`を持たないキャラの扱い

- [x] **剣士にも`mag`の基礎値を少しは持たせる。0にしない**

> **0にすると、`mag`を参照するスキルが将来1つでも付いた瞬間に破綻する。** 「魔法屋ではない」は`allocatable_stats`に`mag`を入れないことで表現できるので、基礎値まで0にする必要はない。

## 5. 戦闘側に足す経路

| 場所 | 何を足すか |
|---|---|
| ダメージ確定の直前 | `crit_rate`の抽選、`crit_dmg`の倍率、`def`／`mdef`の除算 |
| 攻撃タイマー | `atkspd`による短縮 |
| スキルのクールダウン | `haste`による短縮 |
| スキルの威力 | `atk`か`mag`のどちらを参照するかの分岐 |
| ダメージの種別 | **物理か魔法かで`def`と`mdef`を出し分ける**（敵の攻撃にも種別が要る） |

### 着手時に確認する（PLANの記述を信じない）

- [ ] **`attack_interval_sec`と`cooldown_sec`を、戦闘がマスターから直読みしていないか**
  - **装備の第1弾で「戦闘が`get_effective_stats()`を呼んでいなかった」が発覚している。同じ形の見落としの可能性が高い**
- [ ] `battle_controller.gd`が`spd`と`def`を今どう使っているか

## 6. 移行

- [x] **`_recalc_stats()`が毎回レベルから計算し直すため、式を変えれば既存セーブは追従する**

`_recalc_stats()`のコメント：「差分を足し込むのではなく毎回レベルから計算するため、式を変えても既存データが追従する」

**ただし今回はキーそのものが増える。式の変更とは別の確認が要る。**

- [ ] ロード時に`_recalc_stats()`を通す経路があるか確認する。無ければ1回呼ぶだけ
- [ ] **新しいキーが`stats`に無い既存セーブで、`push_error`ではなく0埋めになることを確認する**

> **既存セーブは捨ててよい**（`GAME_DESIGN.md` 14章）。移行処理は書かない。ただし0埋めで落ちないことだけは確認する。
