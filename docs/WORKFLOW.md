# ワークフロー：1つの画面を作るまで

第2層（PLAN）が無い画面を、実装して動作確認するまでの全手順。
役割分担とモデルの割り当ては`PROJECT_STATUS.md`「実装の体制」を参照。

**登場するのは4者。**

| 誰 | 役割 |
|---|---|
| **あなた** | 判断・実機検証・`.tres`と既存ファイルの編集 |
| **設計役**（Claude等） | PLANとEXECを書く |
| **レビュー役**（DeepSeek） | PRE_PLANとIMPL_LOGをレビューする |
| **実装役**（MiniMax） | PRE_PLANを書き、実装する |

---

## 全体像

| # | やること | 誰が |
|---|---|---|
| **1** | PLAN（第2層）を作る | **設計役（Claude）** ＋ あなた |
| **2** | EXEC（第3層）を書く | **設計役（Claude）** |
| — | ↑の指示で`.tres`・既存ファイルを編集 | **あなた** |
| **3** | PRE_PLANを書く | **実装役（MiniMax）** |
| **4** | PRE_PLANをレビューする | **レビュー役（DeepSeek）** |
| **5** | 決定事項をPRE_PLANに書き込む | **あなた** |
| **6** | 実装する | **実装役（MiniMax）** |
| **7** | IMPL_LOGをレビューする | **レビュー役（DeepSeek）** |
| **8** | 実機で確認する | **あなた** |
| **9** | コミットする | **あなた** |

**【3】と【6】は必ず同じモデル・同じ会話で行う。** 自分で書いた計画をそのまま実装するので認識のズレが起きない。実際、倉庫タスクは差し戻しゼロだった。

**【4】と【7】は同じレビュー役でよい。** どちらも渡した資料だけで完結する仕事なので、前の記憶が無くても支障がない。

**設計役は現状Claudeのみ検証済み。** DeepSeekはPLANを書かせると既存の決定を確認せず矛盾した提案をするため不向き（実測）。Geminiは未検証。

**1タスク = 1画面（またはそれに準じる機能単位）。** 大きすぎると事故が増える。

## 【1】PLANを作る — 設計役（Claude）＋ あなた

**渡すもの**

- `PROJECT_STATUS.md`
- `REVIEWER_GUIDE.md`
- `AGENTS.md`
- `SCENES.md`（その画面の位置づけ）
- `DATA_SCHEMA.md` の該当章
- 同規模の既存PLAN（書き方を揃えるため。例：`PLAN_BASE_SCREEN.md`）

**やること**

議論しながら決める。設計役が叩き台を出し、あなたが判断する。

**決めるべきこと**
- スコープ（何を含み、何を後回しにするか）
- 画面構成と遷移
- 使う既存データと、新規に必要なデータ
- 数値（スタミナ消費量など）
- 未確定として残すもの

**注意**

- **既存の決定事項と食い違わないか確認する。** `PROJECT_STATUS.md`の「決定済み」の表が根拠。変える場合は、変えることを明示してその表も更新する
- **スコープを削ることを恐れない。** 検証できないものは作らない（例：アイテムが2種類しかないのにドラッグ&ドロップを作らない）

**成果物**：`docs/01_plan/PLAN_◯◯.md`（全文。あなたが保存する）

## 【2】EXECを書く — 設計役（Claude）

**渡すもの**

- 【1】で作ったPLAN
- **依存する実コード**（`.gd` / `.tscn` / `.tres`）

**実コードは必ず渡す。** PLANは「意図」の記録で、実際のコードとはズレる。PLANだけで書くと、存在しない関数を呼ぶ指示書ができる。

渡すべきコードの目安：
- そのタスクが呼ぶ`GameManager`等の関数があるファイル
- 変更する既存シーンの`.gd`と`.tscn`
- 参照する`.tres`（**中身が空のことがある。必ず確認する**）
- 使う共通コンポーネント

**設計役がやること**

- PLANと実コードを突き合わせ、ズレがあればPLAN側を先に直す
- 事故りやすい箇所を特定し、EXECに名指しで警告を書く
- 完了条件を具体的な数値で書く
- **あなたが担当する作業を切り分ける**（`.tres`の編集、既存ファイルの途中の書き換え）

**成果物**：`docs/02_exec/EXEC_◯◯.md`

**この時点であなたがやること**：EXECで「人間が編集する」とされた箇所を先に済ませる。実装役が参照する定数などは、先に入れておかないとパースエラーになる。

## 【3】PRE_PLANを書く — 実装役（MiniMax）

**渡すもの**：EXECのパス（実装役がプロジェクト内のファイルを読む）

**プロンプトの型**

```
res://docs/02_exec/EXEC_◯◯.md を読んでください。
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
このメッセージではコードを書かないでください。
実装計画だけを立ててください。
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

【手順1：先に実態を確認する】
計画を書く前に、以下を read ツールで読んでください
（bash の cat は出力が読みにくいので使わないでください）。

（依存ファイルを列挙）

【手順2：書き方のルール・厳守】
出力先：D:/pomodoro-heroes/docs/03_log/PRE_PLAN_◯◯.md

1. create_file は使わないでください。トークン上限で失敗します。
2. bash の追記だけを使ってください：
   cat >> "（絶対パス）" << 'EOF'
   （本文）
   EOF
3. 1回のツール呼び出しにつき見出し1つ分。N個あるのでN回。1回60行以内。
4. edit_file は使わないでください。
5. 補助スクリプト（.py など）を作らないでください。
6. 書き終わったあとに読み返し・誤字修正をしないでください。
7. 各セクションを書いたら「セクションNを書きました」とだけ報告してください。
8. 追記する前に、その内容が既に無いか grep で確認してください。

【書く内容】
（見出しを5〜7個。うち1つは必ず
 「判断に迷った点（『特になし』は避ける）」）

書き終えたら止めて、私の確認を待ってください。
```

**見出しの決め方**：EXECの構成に対応させる。最後は必ず「判断に迷った点」。

## 【4】PRE_PLANをレビューする — レビュー役（DeepSeek）

**渡すもの**

- `EXEC_◯◯.md`
- `PRE_PLAN_◯◯.md`
- `REVIEWER_GUIDE.md`
- `AGENTS.md`

**プロンプト**

```
この実装計画をレビューしてください。

判断してほしいのは次の3つです。

1. この計画で実装に進んでよいか
2. 進む場合、人間が決めるべきことは何か
3. 修正が必要なら、何をどう直させるか

判断は、渡したファイルの内容だけを根拠にしてください。
一般的なGodotの慣習より、AGENTS.md の記述を優先してください。

特に見てほしいところ：
- 実装するとクラッシュする箇所がないか
- 計画の中で矛盾している箇所がないか
- 「判断に迷った点」が空になっていないか
- EXECの意図と違う解釈をしていないか
```

**あなたがやること**：レビュー結果を読み、採用するものを選ぶ。**レビュー役の指摘が全部正しいとは限らない。** 指示に従った結果を「違反」と報告してくることがある。

## 【5】決定事項を書き込む — あなた

**PRE_PLANの末尾に章として追記する。** 会話が変わると決定が届かないため、必ずファイルに書く。

```
cat >> "D:/pomodoro-heroes/docs/03_log/PRE_PLAN_◯◯.md" << 'EOF'

## N. 人間による決定事項（実装時はここを最優先で従うこと）

§1〜§N-1 と矛盾する場合は **この章を優先する。**

### N-1.【要修正】...
### N-2.【承認】...
### N-3.【明確化】...
### N-4.【回答】...
### N-5. そのまま採用する判断
（承認する節を列挙）
EOF
```

**タグの使い分け**

| タグ | 意味 |
|---|---|
| 【要修正】 | そのままだと壊れる。直させる |
| 【承認】 | 実装役の判断が正しい。そのまま進める |
| 【明確化】 | 曖昧な箇所の解釈を確定させる |
| 【回答】 | 実装役の質問への答え |

**必ず「そのまま採用する判断」を入れる。** 何も書かないと、承認したのか見落としたのか分からなくなる。

## 【6】実装する — 実装役（MiniMax）

**渡すもの**：4ファイルのパス

**プロンプトの型**

```
以下の4ファイルを読んでください。

1. AGENTS.md（プロジェクトルート）
2. res://docs/02_exec/EXEC_◯◯.md
3. res://docs/03_log/PRE_PLAN_◯◯.md
   §N「人間による決定事項」が最優先です。
   §1〜§N-1 と矛盾する場合は §N に従ってください。
4. res://docs/02_exec/IMPL_LOG_TEMPLATE.md

計画は承認済みです。§N の修正を反映した上で実装してください。

【今回やること】
（人間が対応済みのものを明示し、実装スコープを絞る）

【作業上の注意】
- edit_file は使わないでください
- create_file に長い本文を渡さないでください。
  150行を超えるファイルは bash の cat >> で分割してください
- 既存ファイルを cat > で上書きしないでください。追記は必ず cat >>
- 追記する前に、その内容が既に無いか grep で確認してください
- 補助スクリプト（.py など）を作らないでください
- sed / awk を使わないでください
- 書き終わったあとに読み返して誤字を直す作業をしないでください。
  ただし既存ファイルに追記した直後だけは read で開き、
  編集前の内容が残っていることを確認してください（破壊チェック）
- .tres と autoload/ 配下は一切触らないでください
- project.godot の [input] は変更しないでください
- class_name が認識されないエラーが出たら Godot を再起動してください。
  型指定を Node に落として call() で回避しないでください

【検証について】
実装後、EXEC の「動作確認手順（完了条件）」N項目を
EXEC から項目番号ごと文言ごとそのまま転記し、
1項目ずつ実際に動かして確認してください。
項目を要約したり作り直したりしないでください。

「コードを確認した」「ロジック上正しい」は動作確認ではありません。
「何をしたら何と表示されたか」を書いてください。

実際に動かせなかった項目は [x] を付けず、
「実機未検証」と正直に書いてください。埋めなくてよいです。

【最後に】
IMPL_LOG_TEMPLATE.md の型に沿って
res://docs/03_log/IMPL_LOG_◯◯.md を生成してください。
PRE_PLAN から変更した箇所があれば
「5. 指示書からの逸脱・迷った判断」に必ず書いてください。
```

**最後の「正直に書いてよい」は必ず入れる。** 埋めさせようとすると嘘が混ざる。

## 【7】IMPL_LOGをレビューする — レビュー役（DeepSeek）

**渡すもの**

- `EXEC_◯◯.md`
- `PRE_PLAN_◯◯.md`（決定事項の章を含む）
- `IMPL_LOG_◯◯.md`
- `REVIEWER_GUIDE.md`
- `AGENTS.md`

**プロンプト**

```
この実装ログをレビューしてください。

判断してほしいのは次の3つです。

1. この実装を「完了」として通してよいか
2. 通す場合、人間が追加でやるべきことは何か
3. 差し戻す場合、何をどう直させるか

REVIEWER_GUIDE.md の「3. IMPL_LOGをレビューするとき」に
判断基準が書いてあります。特に「通していいライン」を参照してください。

PRE_PLAN の「人間による決定事項」の章は
それ以外の節および EXEC より優先されます。

判断は、渡したファイルの内容だけを根拠にしてください。
```

**あなたが見るところ**

- 完了条件がEXECの文言どおり転記されているか
- 「検証済み」の中身が実測か、コードレビューか
- 既存ファイルを壊した痕跡がないか（§5に書かれていることがある）

**差し戻す基準**：やっていないのに「やった」と書いてあるとき。**実機未検証と正直に書かれているものは通してよい。**

## 【8】実機で確認する — あなた

**未検証項目を自分で確認する。** どのモデルも完全にはやらない。人間の担当と割り切る。

確認するときの道具：
- ポモドーロ画面のデバッグパネル（デバッグ実行時のみ左上に表示）
- `print`を一時的に足す
- `res://tests/` 配下の検証用シーン

**動かないときは、原因を推測で断定しない。** 切り分けてから直す。

## 【9】コミットする — あなた

動作確認できたらコミットする。メッセージは「◯◯実装」で十分。

**コミットしていない状態で次の大きな作業をさせない。** AIの編集でファイルが壊れたとき、`git checkout HEAD -- <path>`で戻せなくなる。

## AIに触らせないもの（毎回EXECで人間の担当にする）

| 対象 | 理由 |
|---|---|
| `.tres`ファイル全般 | 「値を入れた」と報告して空だった事故 |
| 既存ファイルの途中の書き換え | 末尾追記しか安全にできない |
| 定数ファイル（`state_keys.gd`等） | 既存定数が消えて全画面が起動不能になった事故 |
| 実機での動作確認 | どのモデルも完全にはやらない |
| レイアウト調整 | 指示書を書くより自分で触るほうが速い |

## 迷ったとき

- **設計判断**：`CONCEPT.md`の設計原則に戻る。特に「やって後悔したと思わせない」
- **既に決まっているか分からない**：`PROJECT_STATUS.md`の「横断的な未確定事項一覧」を見る
- **同じ箇所を3回直させている**：実装を止めて設計を見直す（`AGENTS.md`）
- **AIの報告が正しいか分からない**：自分で動かす。それが一番速い
