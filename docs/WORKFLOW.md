# ワークフロー：1つの画面を作るまで

第2層（PLAN）が無い画面を、実装して動作確認するまでの全手順。
役割分担とモデルの割り当ては`PROJECT_STATUS.md`「実装の体制」を参照。

**登場するのは4者。**

| 誰 | 役割 |
|---|---|
| **あなた** | 判断・実機検証・`.tres`と定数ファイルの編集 |
| **設計役**（Claude等） | PLANとEXECを書く。壊れやすいコードは自分で書く |
| **レビュー役**（DeepSeek） | PRE_PLANとIMPL_LOGをレビューする |
| **実装役**（MiniMax） | PRE_PLANを書き、実装する |

---

## 全体像

| # | やること | 誰が |
|---|---|---|
| **1** | PLAN（第2層）を作る | **設計役** ＋ あなた |
| **2** | EXEC（第3層）を書く | **設計役** |
| — | ↑の指示で`.tres`・定数ファイルを編集 | **あなた** |
| **3** | PRE_PLANを書く | **実装役** |
| **4** | PRE_PLANをレビューする | **レビュー役** |
| **5** | 決定事項をPRE_PLANに書き込む | **あなた** |
| **6** | 実装する | **実装役** |
| **7** | IMPL_LOGをレビューする | **レビュー役** |
| **8** | 実機で確認する | **あなた** |
| **9** | コミットする | **あなた** |

**【3】と【6】は必ず同じモデル・同じ会話で行う。** 自分で書いた計画をそのまま実装するので認識のズレが起きない。

**【4】と【7】は同じレビュー役でよい。** どちらも渡した資料だけで完結する。

**IMPL_LOGのレビューは設計役にもさせてよい。** EXECの意図を知っているほど精度が上がる。逆に**PRE_PLANのレビューは設計役に向かない**（自分が書いたEXECの曖昧さは自分には見えない）。

**1タスク = 1画面（またはそれに準じる機能単位）。**

---

## 実装役に渡してよい仕事（最重要）

**ここを間違えると、能力に関係なく破綻する。** 実測で確定した切り分け。

| 種類 | 渡してよいか |
|---|---|
| 新規ファイルの作成 | ✅ |
| JSONの作成 | ✅ |
| 既存ファイルの末尾への追記 | ✅ |
| `print`で結果が出る検証 | ✅ |
| **200行を超える既存ファイルの途中の書き換え** | ❌ 設計役が全文を書く |
| **画面を見る検証**（表示・クリック・遷移・レイアウト） | ❌ 人間が行う |

**実装役は諦めない。** できない課題を渡すと、方法を変えながら試し続けて時間とコストを失う。2回破綻したが、どちらも「できない検証」を渡したことが引き金だった。**能力の問題ではなく、渡し方の問題。**

---

## 【1】PLANを作る — 設計役 ＋ あなた

**渡すもの**

- **`GAME_DESIGN.md` の該当章**（**ゲームの中身の正。第1層**）
- `PROJECT_STATUS.md`
- `NEXT_STEPS.md`
- `AGENTS.md`
- `SCENES.md`（その画面の位置づけ）
- `DATA_SCHEMA.md` の該当章
- 同規模の既存PLAN（書き方を揃えるため）

**やること**

議論しながら決める。設計役が叩き台を出し、あなたが判断する。

**決めるべきこと**：スコープ／画面構成と遷移／使う既存データと新規に必要なデータ／数値／未確定として残すもの

**注意**

- **既存の決定事項と食い違わないか確認する。** **ゲームの中身は`GAME_DESIGN.md`が根拠**（第1層）。実装の進捗・過去の決定は`PROJECT_STATUS.md`の「決定済み」の表。**両方が食い違ったら`GAME_DESIGN.md`が正。** 変える場合は明示して`GAME_DESIGN.md`を更新する
- **スコープを削ることを恐れない。** 検証できないものは作らない
- **既存のPLANを疑う。** 実コードを見ずに書かれたPLANは、存在しない関数を前提にしている。戦闘のPLANは全面書き直しになった

**成果物**：`docs/01_plan/PLAN_◯◯.md`（全文。あなたが保存する）

## 【2】EXECを書く — 設計役

**渡すもの**

- 【1】で作ったPLAN
- **依存する実コード**（`.gd` / `.tscn` / `.tres` / `.json`）

**実コードは必ず渡す。** PLANは「意図」の記録で、実際のコードとはズレる。

渡すべきコードの目安：
- そのタスクが呼ぶ`GameManager`等の関数があるファイル
- 変更する既存シーンの`.gd`と`.tscn`
- 参照する`.tres`（**中身が空のことがある**）
- 使う共通コンポーネント

**設計役がやること**

- PLANと実コードを突き合わせ、ズレがあればPLAN側を先に直す
- 事故りやすい箇所を特定し、EXECに名指しで警告を書く
- 完了条件を具体的な数値で書く
- **完了条件をA章とB章に分ける**（後述）
- **あなたが担当する作業を切り分ける**（`.tres`、定数ファイル、200行超の既存ファイル）

### 完了条件はA章とB章に分ける

| 章 | 誰が | 例 |
|---|---|---|
| **A章** | 実装役 | `print`で結果が出るもの。計算結果・戻り値・状態の変化・JSONの反映 |
| **B章** | **人間** | 画面を見る・クリックする・遷移を見る・レイアウト |

**分けずに渡すと、実装役はB章を成立させようとして必ず時間を失う。** モーダルのタスクでは12項目中8項目がB章相当で、ヘッドレスでクリックを再現しようとして実装が中断した。

**成果物**：`docs/02_exec/EXEC_◯◯.md`

**この時点であなたがやること**：EXECで「人間が編集する」とされた箇所を先に済ませる。定数が無いとパースエラーで止まる。**ただし新規シーンへの遷移先の差し替えは、そのシーンができてから。**

**見出しの決め方**：EXECの構成に対応させる。**最後は必ず「判断に迷った点（『特になし』は避ける）」。**

## 【4】PRE_PLANをレビューする — レビュー役

**渡すもの**：`EXEC_◯◯.md` / `PRE_PLAN_◯◯.md` / `REVIEWER_GUIDE.md` / `AGENTS.md`

**プロンプト**

```
この実装計画をレビューしてください。

判断してほしいのは次の3つです。

1. この計画で実装に進んでよいか
2. 進む場合、人間が決めるべきことは何か
3. 修正が必要なら、何をどう直させるか

判断は、渡したファイルの内容だけを根拠にしてください。
一般的なGodotの慣習より、AGENTS.md の記述を優先してください。

特に見てほしいところ：
- 実装するとクラッシュする箇所がないか
- 計画の中で矛盾している箇所がないか
- 「判断に迷った点」が空になっていないか
- EXECの意図と違う解釈をしていないか
- 既存ファイルの途中を書き換える計画になっていないか
```

**あなたがやること**：レビュー結果を読み、採用するものを選ぶ。**レビュー役の指摘が全部正しいとは限らない。**

実例：モーダルのレビューは「修正不要」と判定したが、`_exit_tree()`で`closed`を発火しない判断には穴があった。**「起きない」と言い切っている箇所ほど疑う。**

---

## 【5】決定事項を書き込む — あなた

**PRE_PLANの末尾に章として追記する。** 会話が変わると決定が届かないため、必ずファイルに書く。

```
cat >> "D:/pomodoro-heroes/docs/03_log/PRE_PLAN_◯◯.md" << 'EOF'

## N. 人間による決定事項（実装時はここを最優先で従うこと）

§1〜§N-1 と矛盾する場合は **この章を優先する。**

### N-1.【要修正】...
### N-2.【承認】...
### N-3.【明確化】...
### N-4.【回答】...
### N-5. そのまま採用する判断
（承認する節を列挙）
EOF
```

| タグ | 意味 |
|---|---|
| 【要修正】 | そのままだと壊れる。直させる |
| 【承認】 | 実装役の判断が正しい |
| 【明確化】 | 曖昧な箇所の解釈を確定させる |
| 【回答】 | 実装役の質問への答え |
| 【却下】 | レビューの指摘を採用しない。理由も書く |

**必ず「そのまま採用する判断」を入れる。** 何も書かないと、承認したのか見落としたのか分からなくなる。

## 【6】実装する — 実装役

**プロンプト**：`docs/PROMPT_IMPL.md`の【C】を使う。

**毎回必ず入れる4つ**

1. **「実機未検証と正直に書いてよい。埋めなくてよい」** — 埋めさせようとすると嘘が混ざる
2. **「未実装と書いてよい。できなかったと報告するのは失敗ではない」** — これが無いと、完成させようとして指示書に無いファイルを作り始める
3. **「1ファイルへの書き込みが2回失敗したら中止」「1つの症状に試す方法は2つまで」** — 方法を変えても回数に数えると明示する
4. **「変更・作成したファイルの一覧を表で報告する」** — 指示書に無いパスが一目で分かる

**B章を検証させない。** 「B章は転記だけして、検証しないでください」と明示する。

## 【7】IMPL_LOGをレビューする — レビュー役

**渡すもの**：`EXEC_◯◯.md` / `PRE_PLAN_◯◯.md`（決定事項の章を含む）/ `IMPL_LOG_◯◯.md` / `REVIEWER_GUIDE.md` / `AGENTS.md`

**プロンプト**

```
この実装ログをレビューしてください。

判断してほしいのは次の3つです。

1. この実装を「完了」として通してよいか
2. 通す場合、人間が追加でやるべきことは何か
3. 差し戻す場合、何をどう直させるか

REVIEWER_GUIDE.md の「3. IMPL_LOGをレビューするとき」に
判断基準が書いてあります。特に「通していいライン」を参照してください。

PRE_PLAN の「人間による決定事項」の章は
それ以外の節および EXEC より優先されます。

判断は、渡したファイルの内容だけを根拠にしてください。
```

**あなたが見るところ**

- 完了条件がEXECの文言どおり転記されているか
- 「検証済み」の中身が実測か、コードレビューか
- **報告された変更ファイル一覧に、指示書に無いパスが無いか**
- **原因を「環境の問題」と結論づけていないか**

最後の項目は特に重要。**キャッシュ・同期・ロールバックといった説明が出てきたら、まず疑う。** 過去2回とも、実際の原因は別ファイルへの誤編集と設計ミスだった。

**差し戻す基準**：やっていないのに「やった」と書いてあるとき。**実機未検証と正直に書かれているものは通してよい。**

**`git status`を必ず見る。** 指示書に無いファイルが増えていないかがここで分かる。

---

## 【8】実機で確認する — あなた

**B章の項目と、未検証項目を自分で確認する。**

確認するときの道具：
- 戦闘画面のデバッグパネル（F3で表示／1〜4で速度／K・L・J・V・B・S）
- ポモドーロ画面のデバッグパネル
- `res://tests/`配下の検証用シーン
- `print`を一時的に足す

**動かないときは、原因を推測で断定しない。** 切り分けてから直す。

## 迷ったとき

- **設計判断**：`CONCEPT.md`の設計原則に戻る。特に「やって後悔したと思わせない」
- **既に決まっているか分からない**：`PROJECT_STATUS.md`の「横断的な未確定事項一覧」を見る
- **実装役が同じ箇所で止まっている**：2回で切り上げさせる。設計側に無理がある可能性を疑う
- **AIの報告が正しいか分からない**：自分で動かす。それが一番速い
